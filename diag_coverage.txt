# diag_coverage.txt —— 诊断覆盖申报清单（发版链第 3.9 关消费）
#
# 这份文件是**堆叠历史**（同 release_checks.txt / release_notes.txt）：新版本往最上面插，
# 不许就地替换上一版那一段。
#
# 为什么要有它：`outputs/诊断导出逐版核查-v1.4.27至v1.4.66-2026-10-12.md` 逐版对账的
# 结论是 39 个实发版本里 29 个引入了当时远程读不出来的状态，而全量回归两年全绿 ——
# "接线"这件事从来没有一道关卡看过。tools/diag_coverage_check.py 现在每轮都问一句：
# 本轮改过的产品模块，诊断包答得上来吗？答不上来就在这里留一行理由。
#
# 形状（只有当前 APP_VERSION 那一段生效，段外一律不认 —— 台账 G26 那条
# "无主的 stale-feature 被下一版继承"就是这个形状）：
#
#     version 1.4.76
#     skip <模块名> <为什么不需要单独接进诊断包>
#
# 三条硬规矩，闸门逐条判：
#   ① 理由为空即拒；② 申报本轮**没改过**的模块即拒（清单只增不减＝没人读）；
#   ③ 模块已被导出面读到（curated）或运行态确实会被 sf_diag 自动采走（auto）时，
#      申报它同样判红 —— 不许用一句"不用接"把真实缺口盖过去。
#
# 一句话讲清这份清单**能**保证什么、**不能**保证什么：它保证每一轮都有人当面回答
# "这个模块坏了用户说什么"，并把答案留在受版本控制的地方可被 review。它不能替你
# 回答得对 —— 理由写错，包里就是空的。所以每条理由都必须写"信息具体从哪一条通路
# 出去"（universe.json / debug.log 的哪一行 / runtime.json 的哪个键），而不是
# "不重要"。
