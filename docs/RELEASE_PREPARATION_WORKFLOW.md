修订：2026-10-21。v1.4.96–v1.4.99 的实际失败、恢复和验收经验归入本流程，不新增另一套发布入口或缺陷台账。

状态：**发布前准备流程**。本文件用于把源码收口、候选构建和正式发布分开管理；它不替代
`build_release.sh`、`DELIVERY_CHECKLIST.md`、`QC_CHECKLIST.md` 或发布后真实场景验收。

适用范围：Apple Silicon、工程内 `.venv`、当前支持的 macOS 版本，以及 Beta/稳定版的每一次
新版本发布。任何一步失败、证据缺失或源码再次变化，都不能沿用后续阶段的结论。

## 一、先固定五种状态

每一轮只允许使用下面的状态，不用“差不多完成”“基本通过”代替：

| 状态 | 含义 | 可以做什么 | 不能声称什么 |
| --- | --- | --- | --- |
| `source_open` | 源码仍在修改或待复核 | 修复、补测试、整理说明 | 候选包同源、可发布 |
| `source_qualified` | 当前源码完成回归和发布前质量核验 | 生成候选包 | 安装、OTA、跨机或远端已通过 |
| `candidate_ready` | 候选 APP/DMG/ZIP/清单已生成，并有同源指纹与证据 | 复核候选，准备不可逆操作 | 已公开发布、用户已升级 |
| `released_pending_acceptance` | 已进入安装/公开发布阶段，可能只完成部分动作 | 先读回实际停点，再做安装启动、升级和回滚验收 | 已全部发布或所有真实场景已通过 |
| `complete` | 规定范围内的发布后验收全部有证据 | 归档并进入下一轮 | 超出证据范围的能力或设备已通过 |

真实场景未完成时必须保留为“未验证”；不使用 `required=false` 绕过常规安装、签名、升级、
OTA rollback、最终启动或其他正式门禁。只有用户永久政策明确列出的四个第三方浏览器专项才可
记录为 `not_applicable` 且 `required=false`，并注明“不等于通过”。

## 二、标准工作流

### P0. 建立发布边界

目标是回答“这次到底发布什么”，而不是先改版本号。

1. 确认工作树、分支、版本类型（Beta/稳定）、目标版本和本轮变更范围。
2. 阅读最近一次已发布记录和最近一次未发布/阻断记录，提取遗留的未验证项、回滚项和真实设备项。
3. 确认本轮不带入并行修改、临时输出、候选包和个人数据；`outputs/` 证据只在本地保存，除非明确属于公开交付物。
4. 为每个用户可见改动指定至少一个行为判据；无法形成包内特征时，指定源码/行为/像素判据，并写入 `release_checks.txt` 或相应测试。
5. 逐一检查相关工作树的未提交增量。来源提交已是主线祖先，不代表工作树内容都已合入；
   将增量分为相同、被主线更新实现替代、确有新增、需语义复核。同名测试文件中的不同判据也不能丢失。
6. 冻结前做既有公开历史只读审计、依赖实时检查和发布协议定向检查。`build_release.sh` 已把历史审计接在
   移动旧产物之前，`--prepare-only` 同样执行；`--local-only` 不因此新增公网发布动作。当前导出树干净不证明旧公开历史干净。
   公开导出审计（`tools/public_release.py`，不带 `--publish`，只读）自 v1.4.105 之后在 `--prepare-only` 里也会跑：
   此前它只在发布阶段才拒绝，v1.4.105 因一条注释里的示例邮箱被拒时候选已冻结，只能退役整个候选重做一轮。
   这也让 `--prepare-only` 变严：导出要求发布输入已提交，主树里别的会话遗留的顶层 `.py`、`.spec` 未跟踪文件会让它在前置核验就报错
   （改走独立发布树）；每次导出还会在 `build/` 下留一个约 15 至 25MB 的 `public_v<版本>_*` 目录，发布收口时随树一起清理。

```bash
./.venv/bin/python3 tools/public_release.py --audit-public-history
./.venv/bin/python3 tools/dependency_audit.py
QT_QPA_PLATFORM=offscreen SF_RERUN_FAILED=0 ./.venv/bin/python3 tools/test_runner.py \
  --module test_public_release --module test_publish_end_to_end \
  --module test_install_guide_placeholders --module test_release_lock_cleanup \
  --module test_release_desktop_staging
```

定向检查用于尽早暴露协议、锁和阶段边界问题，不代替实际合并后的完整关卡。
历史分支不存在只是没有旧历史可审计，不等于未来导出通过；网络失败或漏洞查询不确定不能记为通过。
已占用的同名发行资产不得覆盖，改用新版本。

**基线与范围的取法（v1.4.101 补）**：

- 已发布版本以线上清单为准（带 `Cache-Control: no-cache` 读 `sf_constants.UPDATE_MANIFEST_URL`），
  本机 `build/` 里的发布状态可能停在旧阶段，不作证据。本地版本高于线上就用本地版本，否则递增；
  发行页已有同名资产时不覆盖，改用新版本号。
- “上个已发布版本的源码提交”从该版本的发布记录读出：`publication-vX.Y.Z.json` 与
  `release-state-vX.Y.Z*.json` 的 `source.head` 必须一致，再用 `git merge-base --is-ancestor <基线> HEAD`
  确认它是当前主线的祖先。不要用 `git log -S` 找版本号提交（会取到本版自己的提交），
  也不要拿按版本号推断的区间当基线（诊断核对工具 2026-10-27 前会这样推断，只是估计：
  v1.4.101 并线前取到更早的版本位而偏大，并线后落在旁支提交上而偏小，漏了它自己带来的改动；现在不给基线它直接拒答）。
  读不出、两处不一致或不是祖先时停下问用户，不猜。
- 发布内容 = 开发主线当前提交相对该基线的全部改动。交接里写明基线及依据、提交数、改动文件数和
  有真实代码改动的产品模块。只从开发主线发；其他分支先走并线审查并等用户同意。
- 冻结前先看 `git worktree list`：别的会话若有排队中的并线，发布状态绑定 HEAD，主线一旦前进，
  已生成的候选全部退役。会改变用户可见内容的并线，先请用户决定“等它并入一起发”还是“本版不含”，再冻结。
- 指令里的“发布程度”（完整发布、只备好候选、只在本机安装）留空时，P0 到 P3 的动作完全相同，
  不需要先问；最迟在 P4、第一个不可逆动作之前向用户确认，不默认成完整发布，也不拖到打包之后。
- 主树里若有他人遗留的未跟踪文件（自动化报告、旧版质量记录等），质量闸门会把它们判成本版“未申报改动”，
  `commit_preflight` 对未跟踪的 `.json` 也会提示（工程根目录下的 `quality-v*.json` 质量记录除外，
  它们是证据数据，预检只在报告里如实列出，不再当作执行输入）。它们不属于本版，不能写进范围、不能复用、
  未经同意不能挪动；改用第六节的独立发布树。

建议记录：

```text
版本：vX.Y.Z
阶段：Beta / stable
基线：<上一版提交或已发布候选>
本轮范围：<用户行为、修复、工具或文档>
保留未验证：<设备、系统、OTA、视觉或长期场景>
禁止混入：<并行分支、临时文件、未授权发布动作>
```

**停止条件**：版本范围不清、遗留项未分类、发现用户数据或并行改动无法隔离时，停在
`source_open`。

### P1. 源码和公开资料收口

按同一版本一次性同步，不要先打包后补文档：

1. `sf_constants.py` 的版本号是唯一版本来源。
2. `release_notes.txt` 新增本版段落；按 `1. 内容`、`2. 内容`、`3. 内容` 连续编号，有几项写几项，每项独占一行。
3. `README.md` 的版本、日期、变更正文、下载文件名和限制说明与发布说明一致。
4. 使用 `tools/render_install_guide.py` 更新 `docs/INSTALL.md`，并保留真实的签名、公证、系统和设备边界。
   包内说明稳定引用本版独立 `SHA256SUMS`，不得把包含这份说明的 ZIP 摘要写回说明，形成自引用和打包后输入漂移。
   资产生成前、生成后及摘要改变时，说明正文应相同；实际摘要在独立清单和远端下载中逐项核验。
5. 更新 `release_checks.txt`、`diag_coverage.txt` 及本轮需要的质量/逃逸记录。
6. 运行公开资料检查，不能用手工浏览代替：

```bash
./.venv/bin/python tools/public_docs_check.py
./.venv/bin/python tools/make_update_assets.py --help
```

`make_update_assets.py --help` 仅用于确认工具可用；正式资产由发版链按本版说明生成。

在提交或完整回归之前，再做一次便宜的发布输入核对，避免打完包才发现清单不可用：

- `release_checks.txt` 当前解析器只接受一条有效 `version`，不能把新旧两条有效版本行堆叠；历史说明保留为注释或由 Git 追溯。`diag_coverage.txt` 则按版本段解析，不把两份清单当成同一种格式。
- 除下载文件名外，逐项核对 `checkfile` 中 README、INSTALL 等包内说明的版本字串。单独通过 `public_docs_check` 不证明这些资源判据已经同步。**实做方式**：升版本后列出 `release_checks.txt` 里所有非注释的 `checkfile Contents/Resources/docs/` 行，逐条确认仍是本版版本字串；遗留的 `v<上一版> Beta` 会让候选构建后的 `test_public_release` 红，通常要到完整提交关卡才暴露。
- 用现有 `release_feature_check.parse_checks()` / `gate()` 检查清单结构，并核对 `stale_declaration()` 的版本作用域；这只检查输入，不冒充包内核验。新增符号判据仍由正式工具执行。确实只是固定既有实现重新发行时，如实写版本限定的 `stale-feature` 和补充行为/包内同源证据，不为过关编造新符号。
- 本轮 `quality_trend.py --round` 复盘声明、质量记录范围和公开资料一并收口；零逃逸只表示登记范围内未发现，不代表尚未发布的版本已证明无故障。先用 `--gate <版本>` 检查声明，避免候选后再改受指纹保护的台账。
- 新版说明以普通用户能感知的变化为内容；按用户现行要求（2026-10-23 起由 100 字放宽为 200 字）含标题去空白不超过 200 字；闸门拒绝线与写作上限是同一个数，
  都取自 `tools/release_identity.py` 的 `NOTES_MAX_CHARS`，不再有“拒绝线”与“写作目标”两个口径。
  计数用 `make_update_assets.own_section_text(原文, 版本)` 取出本版段后去空白，与弹窗口径一致；
  范围变化（例如并入了别的改动）后要重写并重新计数，README 的本版正文同步改。
- 逐个有真实代码改动的模块，对基线与 HEAD 的源码做语法树对比，只数顶层定义、模块或类层级赋值和
  `self.` 属性赋值（局部变量会虚增数字），列出“有新名字但清单没查”的模块，再补 `check`。
  只改了函数体或字面量的模块，不拿旧符号凑数，也不用 `stale-feature`（它按整版生效，会跳过整版的
  新增特征判据）；在 `release_checks.txt` 留一行注释写明覆盖它的测试文件和用例，并确认该用例确实存在。
  注释只供人审，不是机器检查，交接里要如实这样说。
- `quality_trend.py --round <版本>` 每次都整条替换该版本的复盘记录：重写时要把全部 `--defense` 和
  `--zero-reason` 一并重新给出；0 逃逸必须写明原因，否则 `--gate` 判红。
- `diag_coverage.txt` 本版段只写本版区间内**真有改动**且需要申报的模块；从上一版整段抄过来的
  `skip` 会被判为“申报了本轮没改的模块”而失败。
- 发版链第 3.9 步（诊断覆盖）**必须**拿到真实发布基线：`build_release.sh` 在质量记录校验之后立即检查
  `SF_RELEASE_BASELINE`，没设就退出码 1，不会走到圆角、二进制兼容和首装路线这些昂贵核验。
  发版前把 P0 读出的基线提交作为环境变量传进去：`export SF_RELEASE_BASELINE=<上一版发布记录的 source.head>`
  （取法见脚本报错里的路径，即上一版 `post_release.json` 的 `release_source.head`）。它必须是 HEAD 的祖先，
  不是提交或不是祖先时工具拒绝下结论（退出码 2），不会悄悄退回推断。
  单独手动跑 `diag_coverage_check.py --version <版本>` 不给基线时（2026-10-27 起）退出码 2 拒答，
  不再按版本号推断区间；手动判定必须写 `--baseline <SHA>` 或 `--range A..B`，后者优先级最高。
- 诊断覆盖的产品模块名单现在取工程根目录下全部 `.py`。v1.4.101 之前只认 `sf_*.py` 加两个点名文件，
  `target_panel` 与 `targets` 一直不在视野里：v1.4.101 里 `target_panel` 有真实改动，却从未被这道闸门核对过，
  用显式基线重跑现在会对它判红。它的诊断归属（接进诊断包，或写 `skip` 与理由）要在下一版的版本段里决定。

**停止条件**：版本、说明、安装指南或下载文件名任一不一致；说明混入未编号正文；出现
占位符、旧版本或未声明的支持范围。

### P2. 源码质量和变更覆盖

先在工程环境中确认运行时，再做完整回归。需要形成发行提交时，先完成全部输入预检和范围审查，
正常提交 hook 执行的同源完整关卡可作为本阶段证据，不先手动跑一遍再由 hook 重跑一遍。
提交后独立核对父提交、审查树、实际提交树、索引及关卡指纹；提交必须早于发布状态初始化与候选冻结，
因为发布状态绑定 HEAD，不能在候选后补提交再沿用原状态。以下命令用于没有本轮有效完整关卡的情况：

```bash
./.venv/bin/python3 --version     # 必须是 3.14.10
./.venv/bin/python3 -c "import PyQt6"
QT_QPA_PLATFORM=offscreen SF_RERUN_FAILED=0 ./run_tests.sh
./.venv/bin/python3 tools/gate_stamp.py check
./.venv/bin/python3 tools/coverage_provenance.py check
```

`run_tests.sh` 全绿后才会写入与构建输入绑定的 `build/.gate_stamp`。如果源码、脚本、spec、
字体、构建基线或文件权限发生变化，必须重新跑完整回归。不得笼统认为文档不影响指纹：README、INSTALL 等也在当前输入名单内，
应按实际 `gate_stamp` 检查；公开资料门禁另外执行。覆盖率凭据还绑定原始解释器入口、配置和数据身份，
即使 `.venv/bin/python` 与 `.venv/bin/python3` 指向相同解释器，也不替换原路径复用凭据，更不能改写凭据消除拒绝。

先登记并清理无解释的 probe/skip/public 模式环境。非空 `SF_GUARD_PROBE`（包括字符串 `0`）不是完整回归。
保存原始退出码和整轮日志，区分故意种错的自检与最终失败；重跑通过不能抹去首败或不稳定记录。
发生进程崩溃时先保留最后用例、线程栈、环境和输入身份，再做最小隔离检查；单模块通过不等于
全量稳定，不能据一次复测给未知根因定性。额外切换 Qt 平台做专项时先核对事件注入、真实曝光、
DPR 与逻辑/设备像素坐标；错误的负向对照或空观测不能证明产品通过，也不能直接证明产品缺陷。
正式检查运行中不另起会改同一覆盖率、应用焦点或用户数据的测试；必要的原生交互验证与完整关卡串行。

起跑前（提交钩子的完整关卡与 `run_tests.sh` 同样适用）先只读确认现场安静：没有别的会话的整轮回归、
提交钩子、合并或 `build_release.sh` 在跑（`pgrep` 看进程，必要时看它的工作目录），屏幕未锁定
（锁屏不等于显示器休眠，`pmset` 看不到，要读会话锁定位），正式版未在运行，且主线 HEAD 与预检时一致。
两轮回归并行会共用临时落盘文件和覆盖率回执，结论互相污染；锁屏会让依赖真实合成的用例成簇误红。
对方的回归在跑就等它结束，不抢跑、不强杀、不另设私有临时目录绕开。

整轮关卡约十几分钟，超过单条命令的时限，放后台跑：日志和原始退出码写到仓库外或本轮证据目录，
用有界轮询等结果，不用 `| tee` 的最后一项冒充退出码。
等待期间能做什么、不能做什么，以及排队与预判工具，见 `COMMIT_WORKFLOW.md` 的“排队与等待期间能做什么”。判断成败看汇总行、结尾行、关卡戳和原始退出码，
不按日志里出现“失败”“冒烟失败”之类字样判断：自检会故意种错并打印这些字样，
只有具体用例结果与最终汇总才算数。

本阶段必须同时确认：

- 静态闸门、PyObjC 桥接形状、底部间距和覆盖率棘轮通过；
- 本轮每个行为改动有对应测试或明确的专项证据；
- 逃逸复盘有真实时间边界，未发现的时刻保持 `null`，不按提交时间估算；
- 本轮真实场景缺口仍单独列为未验证，不被测试数量或覆盖率替代。

**出口**：回归绿、关卡时间戳与当前构建输入同源，状态改为 `source_qualified`。任何红灯或
同源性不明都回到 `source_open`。

### P3. 生成并固定候选

候选生成是可逆的准备动作，使用：

```bash
SF_QUALITY_RECORD="<本轮质量记录绝对路径>" ./build_release.sh --prepare-only
```

候选模式也要求提前提供结构有效的本轮质量记录；结构检查成功不等于真实场景或正式资格通过，
未执行项必须保留未验证和真实非零/待执行状态，不能预填成功 receipt。路径以实际记录位置为准，
不要假设记录总能放在 `build/`：质量工具按记录所在目录解析相对路径，拒绝绝对产物引用、
`..` 和越界软链接。先确定记录基目录能同时容纳候选、日志与附件；例如绑定 `dist/` 与 `build/`
时可使用工程根的私有本地 JSON，明确排除出提交和公开导出。不要为迁移路径修改已冻结记录；
发布完成后按索引原样归档，移动前保留可验证的原路径或重新建立独立归档索引。
首次建立状态时可使用默认路径；失败后新一轮显式设置 `SF_RELEASE_STATE` 的新绝对路径，旧状态保留。

该模式应完成当前源码的 APP、应用 ZIP、DMG、OTA 相关候选和本地证据，但不安装、不上传、不
切换线上清单。候选完成后立即记录：

- 版本三方一致：命令行、`Info.plist`、包内 `APP_VERSION`；
- APP/ZIP/DMG 的字节数和 SHA-256；
- 构建输入指纹、候选 manifest 和质量记录；
- 包内本轮特征、import 闭包、离屏/冻结冒烟、Mach-O 和安装路径核验；
- 两代原生圆角、DMG 真挂载、卷内安装脚本元数据和其他本轮专项结果。
- 候选阶段桌面分发目录前后快照一致；桌面创建、复制新 DMG、回收旧包须晚于正式资格通过，prepared 与普通发布共用该动作。
- 在构建清理前保留版本不同、签名有效的真实旧包，供升级/恢复测试使用，不能拿同版候选冒充旧包。
  做法：用 `ditto` 把 `/Applications` 里当前已装的上一版复制到本轮证据目录的 `old/`，
  再 `codesign --verify --deep --strict` 并确认版本号不同于候选；升级和回退验收都用这一份。
- 质量记录分两阶段，别一次性预填：
  1. `./.venv/bin/python3 tools/release_evidence.py pre-record --root <发布树> --version <当前版本> --baseline <基线 SHA> --limitations-file <限制 JSON>` 起草并绑定三条前置凭据；记录场景保持 `unverified`，不预填任何成功的 receipt。
  2. 候选生成后补真实凭据：用 `quality_evidence.py run <证据目录> --level N -- <命令>` 分别执行
     完整回归日志核对、冻结包冒烟、候选交付验收（`verify_candidate_delivery.py`，其 `--out` 是**文件路径**，
     传目录以前要到最后写报告才失败，升级与回退实际已跑完也不算过；现在工具在做任何事之前就拒绝，退出码 2）。
  3. 绑定脚本只取“退出码为 0 且与当前源码同源”的那一份凭据；失败的凭据原样保留、不引用，
     重跑另生新凭据。记录里引用的产物路径不接受 `..`，而产物分在 `dist/` 与 `build/` 两处，
     所以绑定后的记录与 manifest 放在工程根目录，并把这两个文件名写进 `scope`；写完立刻
     `verify_release_candidate` 自检。发布前记录冻结后不再改写，发布后的验收另建记录（见 P6）。
- 候选与证据按本轮独立目录存放；长步骤放后台，日志和原始退出码落在同一个目录，便于中断后接续。
- 各阶段原生采集使用独立目录；现有同名输出先按原字节、摘要和来源归档，再采集，不覆盖旧截图/result。

候选文件和证据必须放入本轮独立目录，不覆盖上一版本候选。候选生成后如修改任何构建输入，
不得继续使用旧候选，必须回到 P2 重新回归并回到 P3 重建。

**出口**：所有候选资产固定、同源、可回读，状态改为 `candidate_ready`。不能证明本轮修复
进入包内时，必须补充真实包内特征或明确的源码/行为判据，不能用上一轮特征代替。

候选后若修源码、脚本、测试或构建输入，回到 `source_open`，将旧候选明确标为退役并保留索引，重新关卡、构建和取证。
不得把旧圆角/首装/升级凭据贴到新指纹。真实 helper 回滚保留失败注入、真实旧包恢复、旧包首帧和数据哨兵；
短命签名故障载荷是受控注入，不冒充发布 ZIP 自然故障或真实用户线上现场。

### P4. 候选人工复核与发布决策

这一阶段只复核，不重新发明范围：

1. 对照 `DELIVERY_CHECKLIST.md` 和 `QC_CHECKLIST.md`，逐项检查本轮必需项、永久门禁和未验证项。
2. 确认四个发布面相互绑定：源码提交、应用包、DMG、OTA 清单/应用 ZIP。
3. 确认发布凭据、固定签名材料和远端目标可用；缺失时停止，不退回临时签名或假凭据。
   Contents 清单读写都显式绑定 `main`，不以发行仓默认 `public-source` 代替清单目标；
   本地假 HTTP 服务也须正确解析路径与查询参数，不把 `?ref=main` 当文件名。
4. 明确是否有权执行安装、上传、源码公开同步和 OTA 指针切换。没有授权时只停在 `candidate_ready`。
5. 明确绑定本轮质量记录。正式发布命令必须显式传入绝对路径，不依赖终端里残留的环境变量：

```bash
SF_QUALITY_RECORD="<本轮已绑定质量记录绝对路径>" ./build_release.sh --publish-prepared
```

   `build_release.sh` 会在签名、公开历史和产物核验前先检查记录存在且结构有效；这一步失败不应再进入昂贵核验。
   `qualify` 仍会在 APP、DMG、OTA ZIP/清单全部固定后执行，不能用早期结构校验代替正式资格。
6. 对候选目录、manifest、质量记录和命令日志做一次只读归档，记录当前提交和 SHA-256。

此处是发布前最后一个可安全停下的点。候选通过不等于正式发布；本机源码回归不等于冻结包、
安装、OTA rollback、跨机或 macOS 26 实机通过。

### P5. 执行正式发布

仅在 P4 明确授权后执行：

```bash
SF_QUALITY_RECORD="<本轮已绑定质量记录绝对路径>" ./build_release.sh --publish-prepared
```

该模式使用已验候选，不重新打包同一份源码，并执行安装、OTA/公开源码等不可逆动作。脚本的真实
顺序如下；任何中途失败都按实际停点记录，不把部分完成写成“已发布”：

1. 阶段核验与资格检查（`release_state.py validate`、`quality_evidence.py qualify`）：失败时什么都没动，
   状态仍是 `candidate_ready`，修好后可以重跑。
2. `begin-publish`：在第一次不可逆写入**之前**就把状态翻成 `released_pending_acceptance`。
   从这一刻起，中断一律不再是“候选”；重跑 `--publish-prepared` 会在开头的阶段核验处被拒绝，
   因为它只接受 `candidate_ready`。
3. 覆盖桌面 DMG（旧 DMG 进废纸篓）、替换 `/Applications`（旧包移到 `build/_rollback_Skyrocket_*.app`）、
   把更新 ZIP 与清单拷到桌面分发目录。此时**本机已经是新版，线上仍是旧版**。
4. 第 6 步上传 ZIP 并切换线上清单，然后依次是 6.1 安装说明、6.2 公开源码与 DMG、第 7 步源码同步、
   7.1 桌面分发目录对账、第 8 步最终冷启动。第 6、6.1、6.2 步失败会直接退出，其后的第 7、7.1、8 步
   都不会执行；第 7 步和 7.1 步失败只记入结尾结论（分别是“源码未同步”和桌面分发目录遗留项），不回滚已完成的发布，
   仍会执行第 8 步。

按停点记录现场：

- 第 3 步之后、上传之前失败：本机已是新版、线上仍是旧版，发布面尚未开始；
- OTA 上传成功但清单未切换：线上仍是旧版本；
- 清单切换成功但公开源码或源码同步失败：发布面不完整；
- 发布与源码同步都完成，但 7.1 报桌面分发目录与本轮不一致或有待订正的引用：发布本身成立，
  桌面分发目录是遗留项，如实记入收口，订正后重跑 `tools/desktop_folder_sync.py --refresh`；
- 安装替换成功但最终启动失败：发布被阻断，不能宣称完成。

停在第 2 步之后时不重跑整条链，也不靠重复安装来补：`/Applications` 的回退副本只保留最近 2 份，
多装几次会把真正的上一版挤出保留范围。先读回已发生的安装、资产和线上指针，再对剩余阶段单独补做。

**第 6.1 步以后停住：用 `tools/release_resume.py` 续跑（2026-10-26 起）。** 它按脚本原顺序执行 6.1 至 8 步里
还没成功的那些，每步一份日志和退出码；必须步骤失败即停，推送与桌面对账只记录结果，口径与脚本一致。
默认只预演（不创建任何文件或目录），必须前一步已把状态翻成 `released_pending_acceptance` 才肯跑：

```bash
./.venv/bin/python3 tools/release_resume.py run --root <发布树> --state <发布状态文件> --evidence <证据目录>          # 预演
./.venv/bin/python3 tools/release_resume.py run --root <发布树> --state <发布状态文件> --evidence <证据目录> --apply  # 执行
```

**`--root` 必须写成要续跑的那棵发布树。** 默认值是本工具所在的树，而被续跑的发布树里往往没有这个工具
（它在更新的分支上），不写就会拿着这次发布的状态去操作另一棵树，续跑里有公开发布和推送，那是推错源码。
工具会核对状态文件里的版本和提交是否等于 `--root` 的 `APP_VERSION` 与 `HEAD`，对不上直接退 2、什么都不做。

已成功（退出码 0）的步骤默认跳过，失败过的步骤下次自己重跑；`--redo <步骤名>` 点名重做成功过的步骤，
名字必须是计划里的步骤名，拼错直接退 2 并列出可选项（不会静默变成“全部跳过、退出码 0”）。重做时先作废那一步
旧的退出码再执行，所以重做中途被打断，旧的 0 不会继续替它作证。单步超时默认 1800 秒，用
`SF_RESUME_STEP_TIMEOUT_SEC` 调整（低于 60 秒或写错都当场报错，不静默退回默认值）。**第 6 步（上传与读回）
单独一份预算，默认 5400 秒，用 `SF_RESUME_PUBLISH_TIMEOUT_SEC` 调整**（不得低于 900 秒，写错同样当场报错）：
`publish_update_release.py` 里上传一次最多 900 秒、读回最多 4 次每次也最多 900 秒，最坏要 4500 秒以上，
沿用 1800 秒的通用值会在慢上行下把还在正常上传的发布工具整组杀掉，留下半截同名资产，同名重跑又被拒。
没显式设置时取专用默认值与通用预算中较大的一个。每一步自成一个进程组：
超时、Ctrl-C 或收到 SIGTERM / SIGHUP（停止后台任务、关终端）时整组一起杀掉（步骤是 `bash -c`、`node`、`gh`
这类会再起子进程的命令，只杀直接子进程会留下继续写线上的孙进程，重跑再与它们并发；信号默认动作是直接退出，
不装处理器就走不到清理分支，所以等待期间会临时装上、结束后还原，`nohup` 明确忽略的信号保持忽略），
被信号打断时退出码是 128 加信号号，被打断的那一步没有退出码、重跑会重新执行它。
超时记退出码 124 并把已打印的部分和“超时 N 秒”写进该步日志；命令根本启动不了记 127，两者分开。
**证据不新鲜不算“已成功”**：`run` 会拿证据文件的修改时间和“本次发布开始”比，更早的（上一次发布留下的目录）
一律重跑并打印“重跑”，不再把旧的 0 当成这次的完成；`compose` 里本来就有同样的新鲜度检查，两边口径一致。

**第 6 步（上传与清单切换）也能续做：`run` 加 `--quality-record <本轮已绑定的质量记录>`**，就在最前面多出一步
`6-publish`，调用 `publish_update_release.py --resume`。线上已有同名版本 ZIP 时，只有它的大小和读回的字节都与
本地固定快照一致才复用、不重传，接着做发布说明、清单指针、旧客户端清单和线上读回；大小或字节有任何不同，仍然
拒绝复用、拒绝覆盖。不加 `--resume` 时工具行为不变（同名资产直接拒绝）。这样第 6 步断线后不必再手写脚本，
也不必先人工读回——读回是它的一部分。不给 `--quality-record` 就不含第 6 步，和之前完全一样。
补做完后用 `compose` 把原发布日志和各步日志合成一份能过 `post-release` 的发布日志；`6-publish` 跑过的话，
它自己的日志算来源（`published_archive=` 与“线上清单读回一致”正是发布工具真实打印的）：

```bash
./.venv/bin/python3 tools/release_resume.py compose --root <发布树> --state <发布状态文件> --evidence <证据目录> \
    --publish-log <原 publish.log> [--publish-log <第 6 步补做日志>] --out <合成日志>
```

合成规则，缺一条就不写文件、列出缺什么：

- 全部必须步骤退出码为 0 **且各自留有步骤日志**（只有数字、没有日志就无从核对它做了什么），
  来源日志里有“线上清单读回一致”；
- 证据文件的修改时间都晚于状态历史里“进入待验收”的时刻，旧版本留在证据目录里的文件不能沿用；
- “已安装”“版本”“published_archive”三行必须出现在你给的来源日志里，只在步骤日志里出现不算；
- “结论: 冒烟通过”必须出现在最终启动复验自己的日志里：候选阶段（3.6）的冒烟也会在原始发布日志里留下同一句，
  它证明不了最终复验跑过。

满足后才补出脚本在步骤 8 与收尾处打印的两行。合成日志开头写明它不是脚本一次连续运行的输出，并给出每个来源文件
原始字节的 SHA-256；附入时每行只去掉行尾空白（wrangler 表格、git 的 remote 提示带行尾空白，而提交钩子不接受
带行尾空白的文件，归档要入库），内容不改。补出的两行文字由测试拿脚本真实输出核对。**这仍是“续跑证据”，不要把它说成脚本一次连续跑完。**

执行 `--publish-prepared` 之前做一次只读核对，任何一项不符就停下，不进入不可逆动作：

- 发布状态仍是 `candidate_ready`，`release_state.py validate` 通过（源码与候选字节未变）；
  `quality_evidence.py qualify` 通过，用的是本轮绑定好的记录。
- 线上清单仍是上一版；发行页上没有本版的同名资产；`/Applications` 里仍是上一版且程序未在运行。
- 没有别的会话的回归、提交或发布在跑；屏幕未锁；开发主线 HEAD 与候选所绑定的一致。

发布命令放后台跑，日志和原始退出码落在本轮证据目录；本机上行慢时用 `SF_PUBLISH_TIMEOUT_SEC` 抬高上传超时，
不要因此整体重跑。脚本末尾打印“发布动作完成”只表示发布动作做完，状态是 `released_pending_acceptance`，
渠道读回此时仍是未验证，不能据此宣布完成。
脚本结束时（含中途失败退出）会打印“发版链分步耗时”表，列出已完成各步和失败那一步用了多少秒；
它只观测，不参与判定。想知道“慢在哪一步”，读日志里的这张表，不凭印象。

第 7 步源码同步推的是**当前所在分支**：在独立发布树里它会把发布分支推上去并报“已同步”，
开发主线并没有动。发布后另在主树确认可以快进（`merge-base --is-ancestor`、领先笔数），
再单独推送开发主线，并读回领先笔数为 0；发布分支保留，不顺手删除。
推送开发主线用 `tools/release_wrapup.py push`（2026-10-21，默认预演，`--apply` 才推），在主树里执行：

```bash
./.venv/bin/python tools/release_wrapup.py push --branch feat/target-price          # 预演：列出将推送的提交
./.venv/bin/python tools/release_wrapup.py push --branch feat/target-price --apply  # 执行并读回
```

它只推**当前检出**的那个分支（检出的不是 `--branch` 或处于游离 HEAD 就拒绝），只做快进：
远端当前提交必须是本地 HEAD 的祖先，远端落后或分叉一律拒绝，不带 `+`、不带 `--force`，远端没有该分支也不替你首推。
读回用 `git remote get-url --push` 取到的实际推送地址，不用拉取地址；推完远端读回的提交必须等于本地 HEAD，
不等就报错，不信“推送成功”四个字。输出里的地址会隐去内嵌凭据。
它不检查是否有别的会话正在提交或合并；推之前仍按上面的只读核对确认现场安静。

发布锁同时保护原子占位和正常/错误退出的 PID 清理，只删除本进程拥有的 PID，不杀其他任务或删除未知锁内容。
中断后先读回已发生的安装、资产和指针，再按固定 SHA/指纹/路径/字节恢复剩余阶段；不盲重跑整条链或覆盖已发资产。
发布重试时，若源码、构建输入、候选 APP、DMG、OTA ZIP/清单或质量记录发生变化，旧候选和旧收据全部退役，必须回到 P2/P3 重新回归、构建和取证；只有同源且字节未变的候选才允许使用 `--publish-prepared` 复用。
工具误判先用字段含义和正负对照独立核实，不直接去掉检查。历史审计检查全部可达对象，只有真正的
commit author/committer 或 tag tagger 字段中，精确匹配既有 GitHub 账号与获准公开支持邮箱的身份才按公开命名空间识别；
相同字节在 blob、正文、相似账号、其他联系方式或凭据命中时仍拒绝，不笼统豁免整个提交，不因误判强推改写历史。

### P6. 发布后独立验收和收口

发布动作完成后，使用独立读回而不是构建时内存中的结果：

先查询 publication 中固定公开 SHA 对应的 CI 状态，再安排完整独立下载。CI 未完成时只等待该
run/job，不重跑发布、不新推源码、不覆盖资产，也不反复下载同一批文件来等待 CI。
`gh run watch <run-id> --repo <发行仓库> --exit-status` 可等待明确结果；已启动一个等待任务时
不再启动第二个相同等待任务。首轮读回若只是 CI 在运行，保留该次未通过报告；CI 完成后用新
`--out` 路径执行最终独立读回，不手改旧报告。CI 真失败则保留 job ID 与日志，先定位再决定恢复。

1. 读回权威 OTA 清单、应用 ZIP、DMG、源码 ZIP 和校验清单，核对版本、签名、字节数和摘要。
2. 实际下载并校验应用 ZIP/DMG；挂载 DMG，完成安装路线和最终 `/Applications/Skyrocket.app` Cocoa 启动。
3. 复核首帧、持续存活、异常/退出码、更新状态和用户数据未被误改。
3b. **真点击走查装机版**（2026-10-23 补，自动化触发、不在发版链内）：第 2、3 条只证明"包能起来、
   能画首帧"，不证明"包里的界面点得动"。本条用真实鼠标与键盘点一遍最终 `/Applications/Skyrocket.app`：

   ```bash
   ./.venv/bin/python tools/post_release_click_walkthrough.py --report          # 只看前提，不发事件
   ./.venv/bin/python tools/post_release_click_walkthrough.py                   # 客观前提满足时自动真跑
   ```

   覆盖六条动作：`menu`（右键出菜单并点一行）、`drag`（拖主窗）、`chart`（点分时图热区收展）、
   `stretch`（拉下沿改高度）、`stock`（点编辑按钮、敲代码、**点确定**换股票）、
   `target`（点铃铛、加一条目标价、点「立即生效」、再点两下「清空」）。
   判据只看可观测事实：屏上窗口列表、菜单取色、窗口位移与高度、临时 config 里 `code`/`alerts`
   的实际内容、产品自己写的 `ctx menu closed picked=…` 留痕；子进程 `HOME`、图标和旧配置迁移
   同样改道临时目录，字典由 `SF_UNIVERSE_DISABLE=1` 关闭；网络方面，包内带 `SF_REJECT_NETWORK`
   开关的版本由统一入口硬拒绝，**不带该开关的旧包（含已装的 v1.4.103）会真实联网取行情**（只读 GET，
   代理环境变量拦不住），工具会在开头与结论各打一行「网络隔离」并写进 `result.json` 的 `network_guard`，
   验收记录里照抄这一行，不写“产品不出网”；跑完递归比对用户真实支持目录与旧配置的 `(size, mtime_ns)`
   快照，任何文件被改动就当场判红。**工具可由自动化任务直接触发**：它会接管屏幕上的鼠标，
   但正式版仍在运行、屏幕锁定、显示器睡着或驱动进程没有"辅助功能"授权时它退 2 —— 那是"这里答不了"，
   既不算通过也不算失败，不许写成验收项完成，也不许用 `--report` 的输出冒充真跑过。
   **文字输入不等于往前台应用敲字**：Skyrocket 是浮动窗，实测它通常不是
   `frontmostApplication`；`activate()`、合成点击与 `AXFrontmost` 都不能可靠改变这一点。
   但 `CGEventPostToPid` 的系统键盘事件会正常落进它自己的输入框，因此目标价与换股的键盘
   **一律定向投递给被走查 pid**，绝不走 HID 前台通道（否则会把价格/代码敲进用户正在使用的
   另一个程序）。菜单、拖动、拉伸、收展等鼠标动作仍走 HID，保留真实命中与合成判据。
   走查会在弹层位置连续三拍一致、且截图中量到一行文字后才输入；窗口列表出现不等于已经合成。
   目标价默认用面板原生相对写法 `+1%`，避免固定绝对价撞当天涨停（排障时 `1688` 因超过
   当日涨停 1450.34 被正确拒绝）；但包内带网络硬拒绝开关时取不到行情，`+1%` 会被面板拒绝，
   此时工具改敲不依赖行情的整数价 `1000`（`pick_target_price`，见第五节 v1.4.104 一条）。点加号成功后，面板会插入完整列表行并从 193pt 重排到
   约 244pt，底部「立即生效」随之下移；工具必须重新读取 bounds 并按**新坐标**点击，
   再轮询临时 config 直到出现 `above` 的有效目标条目、并等面板关闭。清空同样要等临时
   config 真的回到空列表。换股输入框先 Cmd+A 全选（它预填当前代码）再输入六位。
   菜单行先量截图中第一行文字的中心，且鼠标点击走 0.25 秒前置停顿、0.20 秒按住的慢档；
   快档实测只会收掉菜单并留下 `picked=none`。菜单留痕必须轮询等到收起；只有菜单始终未收起时
   才可按方向键＋Return 兜底，并在证据里写 `method=keyboard`。
   证据 `build/click-<版本>-<时间>/result.json` 随 P6 第 6 条一并归档到
   `outputs/release-candidates/vX.Y.Z/`；有动作判红时先定位再决定恢复，不把 `complete` 写成通过。
4. 按场景矩阵逐项记录通过、未验证、`not_applicable` 和阻断原因；不能用旧版证据或候选证据替代。
5. 生成发布后记录和 manifest 绑定的质量证据；只有规定范围内的真实验收全部闭环，才将状态改为 `complete`。
   命令是 `./.venv/bin/python tools/quality_evidence.py post-release <候选记录> --root <发布树或主树>
   --release-log <publish.log 路径> --installed-app /Applications/Skyrocket.app`，产出 `post_release.json`
   与同名 `.manifest.json`。它要求发布日志里出现六条证据行（安装路径、版本、发布的资产名、最终启动
   复验、冒烟结论、脚本收尾语），任何一条缺失都直接拒绝，不生成半份记录。生成的记录**不**自动改
   `RELEASE_RECORD.json` 的状态，`complete` 仍按 P6 其余各项独立判断。
6. **归档发版证据**（收口后另立一笔提交，2026-10-21 补）：质量记录在仓库根目录和各发布树里是散的，
   不归档就会留下“哪一份才是发出去的”无法回答的未跟踪文件（v1.4.100 实测：主树根目录三份、
   `.sf-popup-release` 两份、`.sf-release-final` 里七份，只有一组与发布回执吻合）。做法：
   以 `post_release.json` 里的 `candidate_sha256` / `candidate_manifest_sha256` 为准，只归档哈希对得上的那组，
   连同它引用的 snapshot、`-complete` 记录、`post_release.json`、`publish.log`、`online-manifest.json`，
   按字节复制到 `outputs/release-candidates/vX.Y.Z/`，复制后逐个重算 SHA-256，并追加进
   `archive-index.json`（每条带 `archived_at`，`from` 写明来自哪棵树）。哈希对不上的早期尝试不归档，
   在该目录 README 里写明原因，免得账本读起来像在描述已发布的版本。归档不改写任何字节、不刷新历史资格，
   也不把 `incomplete` 的发布后记录写成通过。
   命名：`quality-vX.Y.Z[-标签].json` 是发布前固定的候选记录，`…-complete.json` 是读回之后的收口记录；
   标签（如 `-final`）是同版本多次尝试时用来区分的，以发布回执里的哈希认定，不凭文件名猜。

   上面这套手工步骤已固化为 `tools/release_wrapup.py archive`（2026-10-21）：

   ```bash
   ./.venv/bin/python tools/release_wrapup.py archive X.Y.Z --tree <发布树>          # 只预演，不写任何文件
   ./.venv/bin/python tools/release_wrapup.py archive X.Y.Z --tree <发布树> --apply  # 确认清单后执行
   ```

   它按回执里的两个哈希各找出**恰好一份**质量记录，再按 `artifact_fingerprint` 找出同源的 `complete` 阶段记录，
   连同两份 manifest 和 `post_release.json`、`publish.log`、`online-manifest.json` 共七个文件。
   找不到、找到多份、哈希对不上、目标已存在但字节不同、索引里同一路径哈希不同，一律拒绝且不写任何东西；
   复制后重算哈希，不符就在写索引之前停下；已归档的条目再跑一次只报“已归档”。
   **归档副本必须能通过提交钩子的空白检查。** `wrangler` 等工具的列对齐输出可能只在行尾补空格：原始
   `publish.log` 先保留在发布树外的证据目录，再逐行仅去掉行尾空白生成待入库副本，并用这份副本重新运行
   `quality_evidence.py post-release`，让 `post_release.json` 钉住副本的新 SHA-256；不得悄悄改其他字节。
   `archive --apply` 的目标是**运行命令的仓库**（或显式的 `--repo`），`--tree` 只是证据来源。主树有别的会话的
   已跟踪或可执行未跟踪文件时，不要在主树归档或提交：在同一 HEAD 新建干净归档工作树，用
   `archive X.Y.Z --tree <发布树> --repo <干净归档树> --apply` 直接写入那里，仅提交这七份归档文件和
   `archive-index.json`，再快进回主线；不挪动或提交别人的文件。若先误写进主树，先把那批文件和索引差异备份到
   发布树外，逐个核对哈希后恢复主树，再按这条路径重做。
   `archive` 本身不提交、不推送（提交与推送分别见 `commit` 和下面的 `push`），也不替你写该目录 README 的批次说明；归档后的 `post_release.json` 仍保持原状态
   （通常是 `incomplete`），不会被写成通过。
7. **复核桌面分发目录**（用户 2026-10-22 要求，永久规则）：`build_release.sh` 的 7.1 步在 P5 的发布脚本内、
   OTA 发布和源码同步之后自动执行 `tools/desktop_folder_sync.py --refresh`，本条是收口时核对它的结果。它确认 `~/Desktop/Skyrocket/` 里 DMG、更新 ZIP、`Skyrocket-update.json`
   三件版本绑定件同为本轮，ZIP 的字节数、SHA-256、下载地址与清单一致，旧版同族文件没有残留；
   旧一代 `StockFloatTargetPrice-update.json` 是冻结兼容清单，必须仍停在 1.4.54。目录里已登记的 Markdown
   只改写 `SF-RELEASE-SYNC` 标记段（对账版本、发布时间、一键安装脚本现名、正文里已失效的文件引用），正文不自动改字。
   退出 3 表示正文还有待人工订正的失效引用，退出 1 表示发布件或登记不一致；两者都要在收口记录里如实写成遗留项，
   订正后重跑 `./.venv/bin/python tools/desktop_folder_sync.py --refresh` 读回。新增需要跟版本的文档，
   首次用 `--refresh --adopt 文件名.md` 登记。

读回之后到 `complete` 的顺序（v1.4.101 实跑）：

1. 公开 CI 完成后，用**新的** `--out` 路径跑 `release_readback.py`；读报告本体逐项核对
   （`verified`、七个渠道检查、下载文件齐全），不只看退出码。
2. 在自动化任务可接管屏幕、屏幕未锁定且客观前置条件满足时，运行
   `tools/post_release_click_walkthrough.py --out <新目录>`；结果里的六项动作必须全部通过，且 `user_data.ok=true`。它是冻结安装包的交互验收，不由冷启动冒充。
3. 用 `quality_evidence.py run` 为“读回报告已验证”留一份执行凭据。
4. 另建发布后质量记录：先用 `./.venv/bin/python3 tools/release_evidence.py complete --root <发布树> --version <当前版本> --state <状态 JSON> --readback <读回报告> --walkthrough <走查 result.json> --limitations-file <限制 JSON>`，由发布前记录派生，换新的 `change_id`、`release_qualification.stage` 设为 `complete`，
   追加读回的验收条件和凭据，`scope` 加上它自己与 manifest 的文件名，**以及本轮会被归档的
   `outputs/release-candidates/vX.Y.Z/online-manifest.json`、`post_release.json` 与 `publish.log`**；否则后面
   `verify/qualify` 会把这些真实凭据报为“未申报改动”。写完 `verify_release_candidate` 自检。
   发布前记录保持冻结，不改写。
   发布后记录会由 `release_evidence.py complete` 同步调用状态收口；不要再次执行独立的 `release_state.py complete`，避免重复完成或覆盖。
6. 用新的 `--out` 重新生成发布总报告并带上 `--quality` 与 `--readback`。脚本退出时自动生成的那份
   在读回之前，渠道栏会是“未验证”，属于预期，不手改。

源码 ZIP 除版本号和压缩包摘要外，逐文件对照实际公开 SHA 的 Git blob、可执行属性和软链接。
Git archive 的 ZIP 普通文件可能没有完整 Unix 权限字段，不把格式未承载的位推测成 0644 或错误结果。
公开 CI 两项任务绑定同一公开 SHA，保留首次失败、job ID、原始日志和复测；同源复测不是首次全绿，也不证明不再复发。
绘制文案/像素检查主动取得实际帧或有界等待明确事件，不把一次 `update()+processEvents()` 当同步绘制保证，
不放宽断言让空观测通过。收口后再优化流程/工具，另立提交；不改写已发资产、刷新历史指纹或把后续主线当发行源码。

**发布经验自动回写（用户 2026-10-27 起的常设授权，不再逐次确认）**：每次发布走到 `complete`（读回、走查、归档、
主线推送都已完成）之后，把本轮**实测撞到**的坑补进第五节对应版本的“执行经验”，必要时同步修正 P1/P3/P6 里
相关操作步骤。口径：只写有证据的（命令输出、日志行、失败用例名、哈希），推测不写，写了必须标“未验证”；
已发布版本的说明、质量记录和归档证据不改；用与主线同一 HEAD 的干净工作树另立一笔只含本文件的提交，
走完整关卡后快进回主线。授权只到本地提交为止，推送仍按发布流程的常设授权单独判断。完整关卡若因用户数据红线
（`config.json`、`debug.log` 被改）或与本文件无关的原因变红，停下并如实报告，不重试掩盖、不绕过钩子。

## 三、每轮最小证据包

### 自动状态、固定矩阵与发布总报告（2026-10-20）

沿用本流程五种状态与 `quality_evidence.py` 的正式政策，不建立第二套质量账本。
`build_release.sh` 在完整关卡之后创建 `build/release-state-vX.Y.Z.json`：
生成候选之前核验回归戳、覆盖率来源和公开资料，生成候选后固定 APP 目录、DMG、ZIP 和
OTA 清单的内容、权限及软链接指纹。发布既有候选必须先核验 `candidate_ready`；首次桌面覆盖、
安装或远端写入之前记为 `released_pending_acceptance`，中断不会被记录成完成。
`--skip-tests` 不能跳过新状态工具对完整回归的要求，不能与 `--publish-prepared` 混用。

源码、HEAD、已跟踪文档、构建输入或已绑定资产变化后，`validate` 拒绝旧状态。
旧状态不会静默覆盖；保留原始记录后，用 `SF_RELEASE_STATE` 指定本轮新路径，从回归和候选阶段重来。
这也是失败恢复的边界：状态为 pending 时先读回已发生动作，不能重跑发布命令覆盖同名资产。
不要把后续验收写回已固定的发布前质量记录；用另一份同源质量记录保存发布后验收。

脚本退出时自动生成 `<状态路径>.report.json` 和同名 `.md`，保留原退出码；报告失败也不冒充通过。
`report` 退出 0 只表示报告生成成功，阻断项仍看报告内容；放行必须使用 `validate` 和各阶段专用命令。
报告统一列出源码、产物、质量记录及正式场景矩阵。四个永久排除专项与 Intel 能力边界必须保留，
不适用或不支持均不等于通过；`ota_rollback` 仍是必需项。也可随时手动生成：

```bash
./.venv/bin/python3 tools/release_state.py report --state build/release-state-vX.Y.Z.json \
  --quality build/quality-vX.Y.Z.json --out build/release-summary-vX.Y.Z.json
```

有候选交付报告或独立读回报告时，在同一命令追加 `--delivery <候选交付报告>`、`--readback <独立读回报告>`；
工具核对同源后汇总，不把其他候选的通过项搬过来。缺少报告的子项保持未验证。

候选交付工具的每次运行固定记录：候选启动、首装、升级、OTA 正向、失败回滚、关键数据读回和旧版再启动。
未执行项保持 `unverified`。升级和回滚都检查带有目标价、窗口位置、高度和背景模式的隔离配置，
并在新进程使用实际旧包、升级包及回滚旧包内的解析代码核对关键字段和包内版本，缺模块时禁止回退到当前源码；
这层检查不等于冻结新旧版界面已经显示正确，后者仍须真实场景证据。
临时首装也不等于 `/Applications` 已安装或 Gatekeeper 已通过。

`public_docs_check.py` 在打包之前同时检查本版连续编号、200 字上限、README 本版正文和安装指南文件名。
安装指南继续由现有渲染器生成，不维护第二份模板；用语是否面向普通用户仍需人工审阅，不宣称机器能自动判断文案质量。

公开源码发布成功后保存 `build/publication-vX.Y.Z.json`，绑定实际公开提交、源码 ZIP 和校验文件。
发布后运行下面的独立读回：它会实际下载并核对 OTA 签名清单、应用 ZIP、DMG、源码 ZIP、校验文件，
逐文件核对源码 ZIP 与公开 Git blob/权限/软链接，核对主分支公开资料与源码包，确认同一公开 SHA 的两项 CI，
挂载下载的 DMG 并比对卷内应用，最后对同源装机应用验证签名并做 Cocoa 启动。
联网失败、CI 尚未结束、下载不一致、挂卷或最终启动失败均保留失败结果，不记为通过。

```bash
./.venv/bin/python3 tools/release_readback.py --state build/release-state-vX.Y.Z.json \
  --publication build/publication-vX.Y.Z.json --out build/readback-vX.Y.Z-attempt1.json
./.venv/bin/python3 tools/release_state.py complete --state build/release-state-vX.Y.Z.json \
  --quality build/quality-vX.Y.Z-complete.json --readback build/readback-vX.Y.Z-attempt1.json
```

读回不覆写旧报告，重试使用新输出路径。`complete` 仍要求既有质量工具验证全部有效必需真实场景，
并要求同源的七项渠道/最终启动读回全部通过；不能只修改状态文字完成发布。
读回必须发生在本轮进入发布阶段之后，时间需带时区且不能在未来；五份实际下载文件缺一份也不能收口。
公开回执、公开源码和 CI 必须指向同一提交，下载文件须逐一与候选/公开回执的原始字节摘要一致。
三种运行模式互斥，不论参数顺序如何，混用 `--local-only`、`--prepare-only`、`--publish-prepared` 都拒绝执行。
这些工具不自动推送、不自动暂停 OTA，也不包含 P3 发布后健康监控。

每个版本至少保留以下索引，文件可以分散在 `build/`、`outputs/release-candidates/` 和发布记录中，
但必须能由索引定位：

```text
release-preparation-vX.Y.Z/
  source-snapshot.json       # 分支、提交、工作树、构建输入指纹
  quality-record.json        # 回归、覆盖率、静态和逃逸复盘
  candidate-manifest.json    # APP/ZIP/DMG/OTA 资产摘要
  candidate-checks.json      # 包内、签名、圆角、DMG、安装路径等结果
  command.log                # 关键命令和退出码
  acceptance-status.md       # 发布后实际验收、未验证项和阻断项
```

证据必须绑定同一份源码和候选字节。源码变更后重新生成，不覆盖旧证据；原始失败日志保留，
修复后的通过记录另建，不把失败记录改写成通过。

### 两个脚本的编号对照

`run_tests.sh` 的“关”和 `build_release.sh` 的“步”是两套编号，文档与日志里都会出现“第 0 …”，容易混：

| 编号 | 所属脚本 | 做什么 |
| --- | --- | --- |
| 第 0 关 / 0.3 关 / 0.5 关 | `run_tests.sh` | 静态闸门、PyObjC 签名核对、底部两行像素核验，之后才是全量用例与覆盖率 |
| 第 0 步 | `build_release.sh` | 核验回归关卡时间戳，不同源就补跑一整轮 `run_tests.sh` |
| 3.6 / 3.65 / 3.7 / 3.75 / 3.8 / 3.9 | `build_release.sh` | 产物特征、卡片圆角、逃逸复盘、二进制兼容、首装路线、诊断覆盖，都排在 DMG 与安装之前 |
| 4 / 5.1 | `build_release.sh` | 生成并覆盖桌面 DMG；替换 `/Applications` |
| 6 / 6.1 / 6.2 | `build_release.sh` | 上传 ZIP 并切换线上清单；安装说明渲染与核对；公开源码、许可与 DMG 同步 |
| 7 / 7.1 / 8 | `build_release.sh` | 源码同步到当前分支的 origin；桌面分发目录与本轮对账（失败只记结论，不回滚发布）；最终冷启动复验 |

脚本注释里的编号以脚本本身为准；文档引用某一步时写明是哪个脚本。

## 四点五、哪些环节已经自动、哪些还要人催（2026-10-26 盘点）

按 v1.4.105 实际操作逐步对照脚本与日志得出，不凭印象。“人催”指没有工具把它和上一步串起来，每一步之间要人说“继续”。

| 环节 | 现状 | 依据 |
| --- | --- | --- |
| 回归、静态闸门、覆盖率、同源戳 | 自动 | `run_tests.sh`、提交钩子、`gate_stamp` |
| 排队等整档锁 | 自动 | `gate_queue.py commit` / `merge-commit`（有界等待、领票） |
| 候选构建、签名、DMG、圆角门禁 | 自动 | `build_release.sh --prepare-only`（含前置核验与公开导出审计） |
| 发布（安装、OTA、公开源码、桌面对账、最终冷启动） | 自动 | `--publish-prepared` |
| 发布中途断线后的续做（6.1 至 8 步，以及第 6 步） | 自动（本次新增） | `release_resume.py run`（`--quality-record` 含第 6 步） |
| 续做后合成能过验收的发布日志 | 自动（本次新增） | `release_resume.py compose` |
| 分支落地：合并、快进、推送、清理 | 自动（本次新增） | `land_branch.py`，默认预演，推送和清理要单独开关 |
| 证据归档、提交、推送、收树 | 半自动 | `release_wrapup.py archive/commit/push/retire`，每步单独调用 |
| 候选取证（收据）与绑定质量记录 | **自动** | `tools/release_evidence.py pre-record` / `bind`，按当前版本、源码指纹和质量记录自动选择唯一有效凭据 |
| 发布后读回、走查、补发布后记录 | **自动** | `tools/release_evidence.py wait-ci` / `complete`；CI 未完成只等待对应 run，读回和走查结果按新路径绑定 |
| 装机版真点击走查 | **自动触发，客观前提不满足则退2** | 接管鼠标；屏幕未锁定、显示器未休眠、辅助功能已授权、正式版未运行且产物存在 |
| 是否发布、是否推送、是否删远端分支 | **必须人决定** | 不可逆或对外动作，授权不能由工具代替 |

`tools/release_evidence.py` 已把候选取证、绑定、发布后补记录和公开 CI 等待做成入库、按当前 `APP_VERSION` 运行、带测试的工具。
场景限制文字每版不同，必须用 `--limitations-file` 传入，文件含 `pre`、`bound`、`complete` 三个非空字符串数组；工具不替人编写限制，
也不接受缺失、空数组或空字符串。它只负责凭据选择、记录绑定、manifest、verify、qualify 和发布状态收口；安装、OTA 上传、源码推送、
删除远端分支仍由发布流程的显式授权控制，工具不会替它们授权。

仍未串成单一状态机的只有“读回、走查、归档、提交、推送、收树”的外层顺序：现在由 `release_evidence.py`、
`release_readback.py`、`post_release_click_walkthrough.py` 和 `release_wrapup.py` 分段完成，屏幕或权限前提不满足时走查仍退出码 2，
不算通过。以后发布默认按本节顺序自动执行，不再等待口头催促。

## 五、历史经验固化为规则

- v1.4.90 的磁盘空间问题说明：安装路线和 OTA 资产必须分别记账，某一路失败不能推断其他路通过。
- v1.4.91 的公开 CI/远端读回说明：CI、权威清单、CDN、客户端实际下载是不同证据源，必须分开记录。
- v1.4.92 的本机候选说明：本机安装或候选通过不等于已公开发布，也不等于跨设备验收。
- v1.4.93/v1.4.94 的质量证据说明：发布记录必须绑定源码指纹和候选 manifest，未完成真实场景继续保持未验证。
- v1.4.95 的流程改造说明：`--prepare-only` 和 `--publish-prepared` 形成明确的两段式流程；发布阶段不应为了重建同一候选而再次改变源码。
- v1.4.99 的执行经验说明：清单结构、包内说明版本、复盘声明和记录基目录必须在昂贵关卡前核对；正常 hook 的有效全量不重复预跑。候选后补提交需退役旧状态，公开 CI 尚在运行不等于测试失败，也不构成重跑发布的理由。
- 已完成发行的证据先冻结，随后流程维护另成提交；本轮修改不更新历史资产、版本号或公开 SHA，也不把维护后的工作树冒充原发行源码。
- v1.4.101 的执行经验说明：基线从上一版发布记录读出并核对祖先关系，不用版本号提交或默认核对区间去猜；
  他人遗留的未跟踪文件会挡住质量闸门，用独立发布树而不是挪动它们；`--out` 要文件路径；
  `--round` 整条替换；脚本末尾的「发布动作完成」只说明发布动作做完、不等于验收完成；链内诊断覆盖区间按版本号推断、可能偏大也可能偏小，
  发版前要显式给出基线；诊断覆盖的模块名单曾漏掉根目录下的 `target_panel` 与 `targets`。
- v1.4.104 的执行经验（2026-10-26 实跑，下列各条都在那一轮撞到过）：
  - **脚本在 6.2 之后的步骤中途退出时，不能靠重跑 `--publish-prepared` 续上**：第 2 步已把状态翻成
    `released_pending_acceptance`，重跑会在开头被拒。续做办法是按脚本原顺序单独补做剩余步骤
    （公开源码与 DMG、推送、桌面对账、最终冷启动），日志落在证据目录；补做不会让 `publish.log`
    长出脚本自己才会打印的「发布动作完成」，所以 `quality_evidence.py post-release` 会拒绝生成记录。
    **不要手写这一行去过校验**。该缺口已由 `tools/release_resume.py` 补上（见 P5 末尾），v1.4.105 起用它续跑与合成。
  - **发布停在“对外安装说明可达性核对”时，先区分是资产真缺还是检查器误判**：用
    `gh release view` 取资产名、大小、`digest`，与本地 ZIP 比，并读线上清单（`gh api` 读 contents，
    raw 侧有 CDN 滞后）。v1.4.104 实测是误判：GitHub 的最终落点 `release-assets.githubusercontent.com`
    路径末段是 UUID，文件名只在 `rscd` 查询参数里，旧判据只认路径末段。已改为两处都认，文件名不符仍判错。
  - **公开仓 CI 与本机不是同一种环境，新用例要显式声明对环境的依赖**。v1.4.104 公开 CI 有 4 条用例
    只在那里红：启动 `build_release.sh` 的子进程没拨回 `SF_PUBLIC_REGRESSION=0`（脚本会在开头拒绝运行）；
    走查用例默认指向 `/Applications/Skyrocket.app`，空机器上不存在；金标日志用例读 `outputs/`，
    公开快照按设计不含它；更新助手的十六进制校验写成 `[!a-f0-9]`，在 UTF-8 区域设置下大写字母会被放行
    （这条是随包助手里的真缺陷，改成逐字符列出，修复要等下一版随包才到用户手上）。
    写法：子进程测试显式设环境变量、依赖路径的用例显式传路径、依赖私有归档的用例带一份随测试走的摘录、
    shell 字符类不写区间，并让用例在 `C` 与 `en_US.UTF-8` 两种区域设置下各跑一遍。
    本机复现办法：`SF_PUBLIC_REGRESSION=1` 跑那一模块，或把默认路径指向不存在的目录。
  - **公开快照对应已发布版本，不能为了让 CI 变绿重发同一版**。红了就在开发主线修，随下一版的公开源码同步带出去；
    本版的发布记录里如实写“公开 CI 当时红、原因与修复提交”。
  - 提交与候选阶段，**他人的自动化会改动已跟踪文件**（待办自动化追加 `outputs/todo-runs/history.jsonl`）：
    `commit_preflight` 会以 `unstaged_tracked_changes` 拒绝，`quality_evidence` 的工作区指纹也会变。
    做法：先备份并 `git restore --worktree` 该文件、把当天新生成的未跟踪文件移到 `build/` 下并记 SHA-256，
    收口后用补丁放回并核对哈希；不并进发布提交。`gate_queue.py commit` 还要求索引为空（自己按 `--path` 暂存），
    预先 `git add` 过要先 `git reset -q`。`gate_queue.py wait` 的参数是 `--timeout`，`commit` 的是 `--wait-timeout`。
  - 后台任务通知里的退出码不可信（包装进程的码，不是命令的码）：读证据目录里的 `.rc` 文件和 `git log`。
  - `quality_evidence.py` 里 `local_mac` 等真实场景要求凭据层级不低于 3，层级 2 的冒烟会被判“低层级替身”；
    `snapshot`、`impact` 会把结果文件写在质量记录旁边（仓库根目录），用完移走。
  - 圆角门禁新材质（liquid）首次采集有 5 项编辑器可见性检查未过，脚本内置的第 2 次采集全过：
    交付说明如实写“第 N 次通过”，原因未单独定位，不写成无问题。
  - 在另一棵树里并行提交相同内容时，提交前用 `git rev-parse :<路径>` 比较两边暂存区的 blob 哈希，
    相同才可先后落地；不要靠提交说明判断。
  - **顺序：已发布版本先做完读回，再提交任何维护改动**。v1.4.104 实测踩过：发布后先提交了维护改动
    并把待办自动化的文件放回工作树，`release_state` 随即判“发布状态已失效”（它比对整棵工作树的指纹，
    连未声明的改动也算），`release_readback.py` 因此拒绝运行；在固定于发布提交的独立工作树里复核，
    指纹同样对不上。读回要在发布状态还有效时做：发布完成后先跑读回、点击走查、`post-release`，
    证据归档之后，维护改动才另起一笔。
  - **点击走查与“包内带网络硬拒绝开关”的冲突（实测现象 + 推断，未重跑证实）**：v1.4.104 的装机包是第一个
    带 `SF_REJECT_NETWORK` 的版本，走查 6 条里 `target`、`stock` 判红（其余 4 条通过，用户真实目录零改动）。
    产品日志显示走查期间行情请求全被拒；目标价面板的 `+N%` 要用当前价换算（`_apply_pct`），取不到就提示
    “无法获取当前价”、不加条目、面板不关，随后点编辑被产品自己拦下（日志 `btn blocked: edit`）。
    所以更像工具与隔离开关互相冲突，不是已证实的产品缺陷，也不能写成通过。
    对照实验（只让子进程环境不再带 `SF_REJECT_NETWORK`，只跑这两项）两项都过：目标价落盘 1359.48 并清空，
    换股落盘 sz000001，日志里「网络被拒」由 3 条变 0 条且有行情成功记录；但只跑了 6 项中的 2 项。
    **预置行情快照这条路走不通**：产品故意让缓存价不参与目标价换算（`_seed_first_screen` 把判定价置 0、标记为兜底）。
    已改走查工具：包带网络开关时改敲不依赖行情的整数绝对价（`pick_target_price`），读不出开关状态时不猜、仍用 `+1%`；
    用真实面板的判据钉住「无行情时相对价被拒、离线价被接受、有行情时离线价被拒（种子股现价在 1300 以上，
    1000 低于现价；越过涨停线的绝对价另被涨停规则拒绝）」，并用 `run_walkthrough` 的真实流程钉住样本只取一次、
    同一份既交给现场也写进证据。
    **这个改动还没有用完整六项在带开关的装机包上真机重跑证实**，下一次走查要先做这一步。
    （后续：v1.4.105 的六项走查在带开关的装机包上 6/6 通过，此条已闭合。）
- v1.4.105 的执行经验（2026-10-26 实跑，下列各条都在那一轮撞到过）：
  - **卡片圆角门禁的采集连续三次同样判红，根因在探针、不在产品**：启动后约 300ms 有一个 `_force_top` 定时器把
    浮动窗层级重置，探针恰好在它之前设好的层级就被冲掉，编辑器那几项可见性检查于是量到亮底。关掉该定时器
    128/128 通过，在未改动的 1.4.104 源码上同样红，所以不是本轮改动引入。修在探针里（采集前确认层级稳定、
    漂移就重设、并把“稳定与否”作为一项检查写进结果），不是改产品、更不是放宽判据。
  - **候选之后任何一笔提交都会让候选退役**：发布状态绑的是 HEAD 与整棵树的指纹。公开导出审计拒绝了一条
    注释里的示例邮箱，只能提交修复、重做候选，并给发布状态换一个新路径（`SF_RELEASE_STATE`），旧收据全部作废重取。
    这就是上面把导出审计提前到 `--prepare-only` 的原因。
  - **第 6 步上传成功、读回中途断线（IncompleteRead）时不要重跑发布工具**：同名资产已在，旧版本工具会拒绝覆盖。
    现在用 `release_resume.py run --quality-record <本轮质量记录>` 续做：它调用 `publish_update_release.py --resume`，
    只有同名 ZIP 大小和逐字节读回都与本地固定快照一致才复用，不一致仍拒绝覆盖；随后自动做清单切换与线上读回。
    读回是只读 GET，普通断线、5xx、408、429 仍最多重读 4 次，401/403/404 不重读。
  - **独立发布树里部署公开下载入口（6.1）需要 `services/feedback-worker/node_modules`**：该目录不在 git 里，
    新树没有它，`node deploy-pages.mjs` 找不到 wrangler。不要把整个目录做成符号链接——`.gitignore` 的
    `node_modules/` 只匹配目录，符号链接会显示成未跟踪文件，进而触发工作区指纹变化；做成真目录、
    里面逐项指向主树。**v1.4.106 实测：主树自己也没有这个目录**（部署脚本写死
    `services/feedback-worker/node_modules/.bin/wrangler`，而 `services/download-analytics` 本身没有依赖）。
    此时在发布树之外用锁文件装一份：复制 `services/feedback-worker/package.json` 与 `package-lock.json` 到一个
    树外目录，`npm ci`（npm 缓存不全时离线装会失败，需联网；锁文件里的哈希会校验内容），再把装出的
    `node_modules` 里的条目（含 `.bin`）逐项软链进发布树里的真目录。npm 会拦下 esbuild、workerd、fsevents 的
    安装脚本，实测 `wrangler deploy --dry-run` 和 6.1 步部署都不受影响。发布前先用
    `wrangler auth token --json` 只确认令牌存在（不要打印），并跑一次 dry-run，别等到第 6.1 步才发现缺依赖
    ——那时 OTA 清单已经切换。
  - **发布后读回里“公开下载入口”4 次 403**：入口会拒绝 Python 默认的 User-Agent，即使带着正确的检查标记。
    同一标记下实测，默认 UA 403，任何明示的非默认 UA（工具自报、curl、浏览器）都是 302。读回因此全部走了
    回退直连，入口本身并没有被核验到。现在读回下载自报 `Skyrocket-release-readback/1`，不伪装成浏览器。
  - **逃逸台账的严格口径**：只有在线用户、第二台机器、装机现场发现的才计入严格数；“已发布但无人察觉”的条目
    不计。对这类条目不要硬登记一个逃逸来凑数，也不要给不知道的时间戳编数值（写 `null` 并留 `timestamp_audit`）。
  - **“完成”阶段的质量记录是在冻结的发布前记录上派生的**：新 `change_id`、阶段改为 `complete`，加两条验收条件
    （同源发布后读回、装机版点击走查），各绑一份阶段内取得的执行收据；发布前记录与它的 manifest 保持原字节不动。

## 六、主树被占用时的独立发布树

触发条件：`commit_preflight` 或质量闸门指出主树里有不属于本版的未跟踪文件，且它们属于其他会话、
不能写进范围、也不能挪动。此时在**与开发主线同一提交**的独立工作树里完成 P2 之后的全部动作：

1. 新建树与新分支：`git worktree add -b release/vX.Y.Z <新路径> <主线完整 SHA>`；分支名不要复用旧发布分支。
   建之前确认主线 HEAD 仍是该 SHA、路径与分支都不存在。
2. 带上两样不受版本控制的依赖，用符号链接，不复制：工程内 `.venv`，以及本机更新签名私钥（单个文件，
   不要把所在目录里的其他内容一起带进来）。随后 `git status --short` 必须为空，确认符号链接没被收进索引。
   被忽略的测试素材缺了会让对应真链路核验静默跳过，核验报告里要看它是不是走了跳过分支。
3. 关卡戳和覆盖率回执按树各自解析，不跨树复用：新树第一次 `--prepare-only` 会自动补跑完整回归
   再打包，整段约二十几分钟，放后台跑。
4. 旧包、候选、证据、质量记录和发布状态都放在这棵树里；`SF_QUALITY_RECORD` 用这棵树根目录下的绝对路径。
5. 发布后按 P5 在主树补推开发主线，交接写明：发布分支名、是否已推送、树的路径与去留、
   主树里哪些他人文件保持原样未动。树和分支不顺手删除，去留另行确认（用户已明确授权收拾时除外）。
6. 收拾发布树用 `tools/release_wrapup.py retire`（2026-10-21），顺序固定：先 `archive --apply` 并提交，再收拾。

   ```bash
   ./.venv/bin/python tools/release_wrapup.py retire --tree <发布树> --base feat/target-price           # 预演
   ./.venv/bin/python tools/release_wrapup.py retire --tree <发布树> --base feat/target-price --apply   # 执行
   ```

   护栏全部在动手之前检查，任何一条不满足就拒绝，且不动树、不动废纸篓：登记过的、未上锁的从属工作树（不是主树）；
   树的 HEAD 已在基线分支历史里；没有未提交的已跟踪改动；每个未跟踪文件要么在基线里有同路径同字节的提交，
   要么字节与基线已提交的归档索引条目一致且归档副本仍在，要么用 `--allow <路径>` 逐个点名；
   没有进程的命令行提到该树，也没有进程的工作目录在树里（空闲的终端也算）；列不出进程或工作目录时按“无法证明空闲”拒绝。
   通过后整棵树**移到废纸篓**（不是 `rm`），`git worktree prune`，再用 `git branch -d` 删分支，不强删；
   分支被别处依赖时报“kept”而不报错。`--remote` 才会删 origin 上的同名分支，且先证明它已在基线历史里。
   边界：被 `.gitignore` 忽略的内容（`build/` 里的候选与读回、`.venv` 符号链接）不在检查范围内，
   移走前自己看一眼 `build/` 里有没有未归档的发布证据。

独立树里的提交、回归和读回只对这棵树和这个 SHA 有效，不替主树验收；两边 SHA 一致时才可以说两者同源。
