# Skyrocket 日常工作标准流程

适用范围：需求评估、故障修复和日常维护，不包含发布或发布前准备。
本流程不触发构建、安装、上传、签名、权限申请或线上写入，也不修改现有正式质量政策。
准备形成普通本地提交时，统一转入 [COMMIT_WORKFLOW.md](COMMIT_WORKFLOW.md) 的 C0-C5；
本流程的验证档位不豁免提交 hook 的完整关卡，开发完成本身也不构成提交授权；
提交授权的依据见 [COMMIT_WORKFLOW.md](COMMIT_WORKFLOW.md) 第 1 节（含 `AGENTS.md` 的持续执行授权）。

## 1. 每个任务的最短路径

1. **确认**：阅读 `AGENTS.md`，检查 `git status --short` 和本轮涉及文件的差异，确认当前分支、
   源码版本和用户实际运行对象。保留并行修改，不能把源码、安装版和临时副本混为一谈。
2. **查重**：先找已有实现、测试、工具和最近相关记录；从相关模块向外查，不默认全仓重审。
   已有能力可解决时，选择配置、解释或诊断，不为同一问题重造功能。
3. **定范围**：用[任务模板](DAILY_WORK_TEMPLATES.md)写清现象、目标、非目标和可观测判据。
   普通小改可放在任务对话中；复杂、易中断或需要证据的任务才另留本地记录。
4. **验证假设**：先用一个最小样本、行为测试或只读观察验证主要假设。不能验证时记录缺口，
   不把猜测写成根因，不先进行大规模改写。
5. **实施与验证**：按下表选择专题，最小行为验证通过后扩大到关联模块；共享基础设施、
   线程、原生窗口和跨模块协议的修改扩大验证，不以专题导航作为测试范围上限。
6. **交接**：给出改了什么、执行过什么及其结果、证据位置、未验证项和下一步。
   没执行的命令标为建议；没有证据的真实场景不能记为完成。
   实现完成后、交给提交流程之前，先按 [CLOSING_WORKFLOW.md](CLOSING_WORKFLOW.md) 收尾。

### 先按风险决定工作量

下表是选择验证范围的下限，不是豁免表；存在多种情况时取较高档。风险来自行为影响，
不是文件数或行数，不能把“只改一行”作为降低验证的理由。

| 档位 | 适用情况 | 最小动作与结束条件 |
| --- | --- | --- |
| 轻量 | 纯文档/说明且不改变执行含义 | 核对事实、命令、链接和差异；说明没有执行过的步骤，不要求跑无关产品测试 |
| 关联 | 局部确定性逻辑或可隔离的工具行为 | 最小行为及失败反例 + 直接调用者的关联测试；行为判据满足、无未解释失败后结束本次源码任务 |
| 扩大 | 持久化协议、线程/退出、原生窗口、共享网络/调度、依赖或测试运行器 | 关联测试 + 跨模块/故障路径 + 按现有规则完整关卡；真实场景仍单独验收 |

每轮开始只需明确目标、运行对象、非目标、判据和验证档位五项。其余字段按需要填，
小任务不强制写长报告。不能因完整关卡被正式版运行守卫阻止而降低档位或强关用户进程；
可继续安全的定向验证，交接时写明完整关卡尚未执行。

### 共用的结束判据

- 每个承诺改变的行为都对应一个实际观察结果；命令退出码、失败、错误、跳过和 flaky 分开记录。
  全部跳过或零用例不证明行为通过，重跑绿也不自动消除首次失败。
- 必需判据失败或缺证据时，不写本任务已完成。可以交接已实现部分，但必须明确未完成项、原因与下一步。
  若任务只要求源码修复，不把未授权的安装/发布扩大为任务；也不能宣称真实故障已经关闭。
- 出现范围扩张、输入/源码/环境变化或意外用户数据写入，先停下受影响操作，重新定界和核对证据。
  不自动清理现场、覆盖备份或把其他会话的改动算成本轮修改。
- 涉及分支合入时转到既有 `BRANCH_MERGE_WORKFLOW.md`；日常验证不自动授权合并或推送。

| 场景 | 先用哪条流程 | 测试导航主题 |
| --- | --- | --- |
| 新需求、优化建议、全面检查 | 2. 需求进入 | 识别影响面后选择，不默认全部 |
| 用户报错、崩溃、功能失效 | 3. 故障闭环 | `diagnostics` 加实际受影响主题 |
| 行情、分时、搜索、日期或主备源 | 4. 数据正确性 | `data`，通知相关加 `targets` |
| 配置、目标价保存、缓存和恢复 | 5. 持久化 | `storage`，业务相关加 `targets` |
| 布局、绘制、材质和窗口交互 | 6. 界面与原生窗口 | `ui`，线程/退出相关加 `lifecycle` |
| 启动慢、输入卡、CPU 或内存异常 | 7. 性能决策 | `performance` 加实际受影响主题 |
| 日常修改、测试选择与失败归因 | 8. 验证选择 | 对应主题，工具/门禁加 `infrastructure` |
| 中断恢复、换聊天、长任务结束 | 9. 任务交接 | 不因交接重复执行已有效验证 |

## 2. 需求进入：先决定是否开发

- 明确用户行为和痛点，不把用户提出的实现方法直接当成唯一解法。
- 搜索相关模块、调用入口、历史记录和测试，回答是否已经存在，是否只是没有生效。
- 写清本次范围、禁止混入的变更，以及成功/失败各是什么可观测结果。
- 采用现有模块和帮助函数；新抽象必须消除实际复杂性，不顺带重构无关代码。
- 选择“开发、修复已有能力、调整配置、补诊断、暂不实施”之一，并说明理由。

**停止条件**：需要改产品行为但目标矛盾，或涉及数据删除、权限、外部服务和未授权写入时，
先澄清必要问题；其余能以安全默认值推进的工作继续，不用模板增加等待。
普通网络/数据代码修改不因“涉及外部服务”自动暂停；需要另行确认的是实际启用服务、发送数据、
付费、申请权限或超出现有授权的远端写入。离线夹具和不改变现场的分析可以继续。

## 3. 故障闭环：先保现场，再改实现

1. 确认实际版本、运行路径、操作顺序、发生时段、预期与实际结果。涉及交易时段时记录时区。
2. 保留当时日志、诊断包、截图或原始回包；脱敏并限制读取范围。原始证据不覆盖，失败日志不改绿。
3. 已发布缺陷在发现现象时立即按 `AGENTS.md` 使用 `tools/quality_trend.py --open`；根因明确时
   立即 `--rootcause`。历史证据不能支持的时刻保持未知，不借提交时间或本次记账时间倒推。
4. 按“输入/数据 → 后台任务 → 状态传递 → 持久化 → 表现”定位，用实验区分假设。
5. 先补能暴露旧错误的行为判据，再作最小修复。能够安全执行时，在隔离进程/临时夹具中证明
   修复前失败、修复后通过；不得为负向对照回退用户工作树或触碰正式安装。
6. 关联验证后记录实际边界。源码修复可以交接，但安装版/用户现场未验证仍单独保留，
   不据此提前关闭依赖真实场景的缺陷。

如果定向实验已无法区分假设，不无限扩大搜索：列出现存假设、各自反证与缺失的现场信息，
优先补能区分它们的一个观测。缺少用户现场才能推进时一次说明所需最少信息；
网络故障、停牌/非交易时间和数据源返回旧值先区分，不能用增加重试次数掩盖未知根因。

已有入口：`sf_diagnostics.py`、`sf_diagnostics_controller.py`、`tools/diag_coverage_check.py`、
`tools/diagnostic_closure.py`。诊断上传边界见[本地协议](DIAGNOSTIC_FEEDBACK_PROTOCOL.md)；
本地协议实现不代表真实用户自动上传已实现或获授权。

## 4. 数据正确性：沿一条链检查

每次数据修改都核对：**原始回包 → 解析 → 股票/来源交易日 → 队列与业务状态 → 缓存 → 界面**。

- 明确来源字段、单位、时区和日期口径；接收时间不是成交时间，写入日不是分时归属日。
- 复用既有离线夹具，覆盖空结果、非法/非有限价格、重复分钟、乱序、跨日、缺日期、主备源失败、
  切股晚回包和恢复后的同点集重绘。新样本必须最小化、脱敏，不能包含个人凭据。
- 同时检查目标价业务与可丢弃显示帧的区别，不能因队列合批丢失已收到的触发价格。
- 真实接口只做必要的低频只读核对，不默认联网，不以一次在线成功证明稳定性，也不把模拟
  主备切换写成真实备用源在线可用。

参考：[分时恢复全链路走查](MINUTE_RECOVERY_AUDIT_2026-10-15.md)。
数据正确、计算正确、结论可靠和展示一致分别核对，未知日期或未知新鲜度不能用推测补齐。

## 5. 持久化：保存必须经得起新进程读取

先区分不可随意丢弃的用户配置与可重建的缓存，不能用同一种降级/清理策略。

1. 使用临时目录，在首次导入产品模块前注入相关路径；复用测试隔离底座，不触碰真实配置。
2. 验证“提交值 → 实际文件 → 新进程读回 → 用户看到的值”，不能只断言 `save_*` 返回成功。
3. 按修改范围验证权限不足、写入失败、主文件损坏、备份损坏、旧格式迁移、未知字段保留和恢复。
   平台支持时验证中断写入；不能模拟的故障明确列为未验证。
4. 涉及异步写入时检查快照副本、合并策略、退出等待/超时和失败反馈；不把排入队列当作已落盘。
5. 用户数据恢复先备份、只读诊断，再按明确授权恢复；不自动删除损坏原件或覆盖可用备份。

已有实现入口：`sf_config.py`、`sf_storage_tasks.py`、`sf_target_controller.py`、
`sf_target_lifecycle.py`。本流程不宣称这些模块已经完成全部故障场景验收。

## 6. 界面与原生窗口：按问题类型选证据

| 类型 | 首选验证 | 不能替代的证据 |
| --- | --- | --- |
| 布局/文字间距 | 加载项目字体后离屏渲染、相对几何和像素断言 | 原生层级和跨 Space 行为 |
| 绘制/缓存 | 同数据同尺寸前后图像、失效条件和重绘行为 | 安装版实际显示 |
| 原生材质/层级 | 真实 Cocoa 探针、可见性和交互观察 | 其他机器或系统 |
| 生命周期 | 展开/收起、最小化恢复、退出和线程清理 | 长期运行或真实唤醒 |

先固定修改前的场景与判据，修改后使用同尺寸、缩放、背景和窗口状态比较。只覆盖本次影响面，
不要每个小布局改动都重做所有人工专项。真 AppKit 路径按既有规则使用子进程 harness。

复用 `tools/verify_bottom_gap_px.py`、`tools/native_glass_probe.py` 与
[弹层材质说明](POPUP_MATERIAL_VALIDATION.md)。原生探针可能显示窗口、改变 Space 或生成截图，
先核对参数和影响，不由测试导航自动启动。连续视频仅本地保留。

**政策边界**：不得增加豁免。仅既定四专项可记录 `not_applicable` + `required=false`，并注明
“不等于通过”；常规自动全屏、签名、安装、升级、OTA rollback 等原有必需项不变。
Intel ARM 包边界仍是“不支持，不代表通过”。

## 7. 性能决策：测量后才决定改不改

1. 分类：启动、输入响应、主线程阻塞、请求等待、CPU、内存增长或资源释放，不混用指标。
2. 固定同一机器、源码、数据、窗口状态、采样区间和工具参数，保留原始基线与干扰因素。
3. 用现有工具定位主要成本，一次只改变一个主要变量；先排除网络、系统负载和测量方法差异。
4. 同条件多轮复测，报告分布、波动和未覆盖场景；基准结果不直接成为跨机器固定毫秒门槛。
5. 收益不可复现或复杂度大于收益时，撤回本次优化或暂缓，不触碰用户的其他修改。

已有工具：`tools/performance_audit.py`（隔离微基准）、`tools/coldstart_bench.py`（源码启动）、
`tools/input_latency_probe.py` / `tools/typing_latency_probe.py`（交互探针）、
`tools/resource_soak.py`（有界资源观察）。调用前阅读工具说明和 `--help`，单独确认窗口、
应用启动、输出路径及调度影响；不要将有调度能力的工具当作默认自动巡检。
RSS 增长不是泄漏定论，系统负载不是应用归因，源码基准不是冻结包启动验收。

## 8. 日常验证：快速反馈不降低正式门禁

环境必须为工程 `.venv` 的 Python 3.14.7 + PyQt6。以下命令从仓库根目录执行：

```bash
./.venv/bin/python --version
./.venv/bin/python -c 'import PyQt6'
./.venv/bin/python tools/daily_workflow.py --list
./.venv/bin/python tools/daily_workflow.py --topic data --topic storage
./.venv/bin/python tools/daily_workflow.py --check
```

导航只打印命令，不执行、不导入测试模块、不请求网络、不读取用户配置、不写关卡戳。
`--topic` 只检查所选主题，无关主题损坏不会阻断；`--check` 检查全表。空主题、重复登记、
非法模块名、缺文件、错误语法和指向仓库外的目标均拒绝；多个主题之间共享模块自动去重。
静态检查只确认顶层有带同步 `test_*` 方法的有基类类定义，不能证明基类就是 `TestCase`、
导入可用、运行时可加载、测试通过或覆盖完整。仅继承测试、动态生成或自定义 `load_tests`
等特殊入口需要单独评审，不能为通过导航伪造一个空测试。

生成命令使用当前工作树的绝对路径，可从其他目录执行，并调用既有 `tools/test_runner.py --module`，
在导入产品代码前建立独立临时配置、缓存、日志和 socket 路径，禁用证券字典自动拉取与首屏预填；
结束后清理临时目录、恢复原环境。继承单用例超时、弹窗拦截及用户数据前后检查；
它不是阻止所有文件/网络访问的沙箱，也不能替已导入产品模块重新绑定常量，须在新进程执行。
命令默认 `SF_RERUN_FAILED=0`，不以自动重试掩盖首次失败；运行器加载到零用例直接失败。
真正执行命令会导入产品/测试模块并运行夹具，仍须先检查测试隔离；只读承诺仅属于导航本身。
单用例超时不覆盖导入阶段，也不是整轮执行时限；导入卡住、原生崩溃和进程残留须单独排查。
如果手动开启重跑或随机顺序，应在记录中保留环境变量和 flaky 情况。

新增/移动测试或改变工具 CLI 时同步维护主题表，运行导航 `--check`、自身测试和受影响的运行器测试。
主题是人工维护的起点，不是依赖图；未列入主题的新代码必须自行补测试，不能宣称“导航通过即覆盖”。

验证层次：最小复现/新增行为测试 → 导航关联测试及实际调用者 → 共享影响面扩大验证 →
按既有规则执行提交/全量门禁。指定模块虽复用运行器保护，仍不包含 `run_tests.sh` 的全部前置检查、
覆盖率与关卡戳；不得随意加入未审查的测试。测试仍须遵守 `AGENTS.md` 的隔离、子进程、
固定时钟和 `SFCase` 约定。新增测试类按纪律扫描要求继承 `SFCase`。

正式全量入口保持原样，先遵守正式版运行守卫，不为跑测试强制退出用户进程：

```bash
QT_QPA_PLATFORM=offscreen ./run_tests.sh
```

失败时保留第一次失败证据，先判定产品回归、测试污染、环境问题还是不稳定用例。
重跑通过不能抹掉首次失败；不得通过提高基线、跳过、降低断言或改期望值使其“变绿”。

| 失败形态 | 下一步 | 不允许的处理 |
| --- | --- | --- |
| 解释器/依赖缺失、导航目标失效 | 修复环境或登记；未运行的测试继续未验证 | 用系统 Python 顶替、把工具故障算产品通过 |
| 可重复行为失败 | 保留输入与首败，定位产品或夹具的实际错误 | 只改期望值或删测试 |
| 单独绿、组合红或重跑绿 | 检查共享状态、清理、时钟和顺序，保留 flaky | 反复重跑到绿便关单 |
| 超时、崩溃、用户数据变化或真实桌面弹窗 | 停止当前验证，保留线程/进程/数据证据，先处理测试安全性 | 自动重启正式应用、恢复/覆盖真实数据掩盖现场 |
| 守卫阻止全量运行 | 保留守卫结果，等待安全执行条件 | 绕过守卫或强退用户进程 |

## 9. 交接与复用：复用结论之前先核对边界

- 短任务在对话结尾使用[交接模板](DAILY_WORK_TEMPLATES.md)，长任务可留本地证据索引。
- 记录分支、HEAD、相关未提交改动、测试输入/环境、命令、退出码和证据路径。
  HEAD 相同不代表源码相同，时间相近也不代表证据仍有效。
- 若已有同源指纹，引用原记录；否则记录实际验证文件及摘要/差异。依赖、配置、上游协议或
  关联调用者改变时重新判断验证范围，不能只比较一个文件来宣布整条链仍有效。
- 复用前核对工作树、相关文件（含未跟踪文件和执行权限）、测试/夹具、运行时依赖、配置、
  系统/显示环境和数据时间边界。没有足够绑定信息的旧结论只作调查线索；线上可用性、实时行情、
  当前权限和窗口状态等时效性事实必须重新观察，不因源码未变而复用。
- 日常导航不生成同源证明。正式关卡戳只由既有完整入口生成；不能手写、复制或用定向运行补戳。
- 恢复任务先读交接、查工作树差异，只补失效或缺失的验证，不因换聊天重复扫描全仓。
- 原始日志/回包/视频保持本地、脱敏和不可覆盖，不默认提交、公开或自动上传。

## 10. 轻量记录与成效复盘

不新增数据库、不新增自动巡检、不为每个小改强制生成文件。缺陷唯一账本继续使用
`tools/escapes_ledger.json`，模板只引用 ID 和证据，不复制另一套状态或时间。

复杂任务确需留档时，优先用仓库外的新建目录；需要仓库内证据索引时才选择
`outputs/daily-work/<任务标识>/`，先检查忽略规则和内容。未跟踪不等于忽略、忽略也不保证
构建指纹不受影响；完整关卡和合并证据按更严格的仓库外规则保存。不默认提交原始证据。

可在后续若干实际任务中观察重复调查次数、返工次数、验证耗时和复发情况。记录实际可证明的
数据和同口径分母；缺基线保持未知，不补估算定位时间、不承诺节省百分比。
本流程与导航的落地不等于效率已提升，实际收益仍待使用记录验证。
