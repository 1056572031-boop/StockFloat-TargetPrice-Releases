# Skyrocket 日常提交标准流程

制定日期：2026-10-19。适用于本仓库后续所有普通新提交，包括功能、修复、重构、测试、
工具和文档提交。提交指将明确范围的修改保存为一个可追溯的本地 Git 版本。
这是执行规约，附只读预检工具，不是自动提交器，也不代表本次已执行提交。
复核日期：2026-10-20；补齐身份冲突、途中扩围和隔离树回到原树的处理，不削弱完整关卡。

## 日常短路径

通常只需四次操作，不必逐轮机械执行本文所有参考命令：

| 操作 | 对应阶段 | 只做什么 |
| --- | --- | --- |
| 一次确认 | C0-C1 | 确认授权、范围和现场；审查行为，执行必要定向验证 |
| 一次整理与预检 | C2-C3 前置 | 整理准确路径、运行只读预检；有阻断先解决，不提前跑完整关卡 |
| 一次正式提交 | C3 | 固定树及输入快照；正常 hook 执行完整关卡，保留原始日志和退出码 |
| 一次读回与交接 | C4-C5 | 核对实际提交、索引及输入；填写同一份短交接，发布/合并不在本流程 |

任何一步改变范围或验收输入，仅回到受影响阶段，不重复无关审查。C0 的身份、归属和敏感数据
判断不能交给工具自动批准；C4 的实际提交核对也不能用提交前预检代替。

## 1. 范围与边界

- 开发与问题验证先走 [DAILY_WORKFLOW.md](DAILY_WORKFLOW.md)，实现完成后先按
  [CLOSING_WORKFLOW.md](CLOSING_WORKFLOW.md) 收尾，准备提交时统一进入本流程。
- 分支合并及其合并提交仍走 [BRANCH_MERGE_WORKFLOW.md](BRANCH_MERGE_WORKFLOW.md)；
  发布准备及发行提交仍走 [RELEASE_PREPARATION_WORKFLOW.md](RELEASE_PREPARATION_WORKFLOW.md)。
  本文不重定义它们的步骤、授权或验收标准。
- 用户要求实现需求本身不构成提交授权。授权依据有两种：用户明确要求本轮提交或约定可提交的任务范围；
  或 `AGENTS.md` 开头的持续执行授权（2026-10-20），它把任务范围内的本地提交列为默认授权，满足本流程的授权确认，
  但不扩大本轮范围，用户后续明确的暂停、只读、范围限制或撤销授权优先。两者都没有时停在“待提交”，
  不为执行标准擅自提交。
- 本地提交不自动授权推送、版本升级、打包、安装或发布。对于合并，执行者自建、已提交且审查闭环的
  任务分支适用 `BRANCH_MERGE_WORKFLOW.md` 第 1.1 节的常设授权；其他分支仍须取得用户同意。
  本文止于本地提交核验和交接，不包含远端同步操作，不修改现有正式质量政策。发布流程所需的推送、
  打包、安装与 OTA，另由 `AGENTS.md` 的持续执行授权和发版入口约束。
- 一次提交表达一个可解释的目的。实现与直接相关测试一起提交；无关修复、重构、
  发布资料和其他会话的工作不顺手带入。确有不可拆依赖时说明理由和完整范围。

## 2. C0：确认现场和提交范围

先只读检查，不清理现场。以下是需要时展开的参考命令，已有有效输出可引用，
不是每次必须重复输出的清单；失败先解释，不能继续机械套用：

```bash
pwd
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short --branch
git status --porcelain=v1 --untracked-files=all
git diff --stat
git diff --cached --stat
git ls-files --others --exclude-standard
git worktree list --porcelain
git var GIT_AUTHOR_IDENT
git var GIT_COMMITTER_IDENT
git ls-files -v
```

1. 确认仓库、工作树、分支、起始完整 SHA、本轮目的、允许提交的路径和用户授权。
   detached HEAD 或正在 merge/rebase/cherry-pick/revert 等特殊操作中时，不套用普通路径，
   先明确原操作和恢复方案；不自动切分支或续作。开发主线名称不等于本轮必然应提交到主线。
2. 将暂存、未暂存、未跟踪文件分为本轮内容、并行内容和归属未明内容；先读差异再决定归属。
   已暂存文件也不等于已获准提交。归属不明不纳入，不撤销别人的暂存。
3. 检查实际生效的作者和提交者身份，不能因历史提交使用某个身份就沿用或修改为该身份。
   出现非预期身份先确认，不擅改全局/仓库身份，不回填作者或时间。
4. 不使用 `git add .`、`git add -A`、`git commit -a` 批量兜底，不自动 stash、清场或删除工作树。
   无法隔离范围时暂停实际提交，说明具体冲突；不要求为此次提交清掉所有并行工作。
5. 在普通终端检查继承的 `GIT_*` 路由变量、命令级配置和特殊索引；目标必须是本工作树的默认索引。
   出现 `GIT_INDEX_FILE`、`GIT_DIR` 等路由覆盖时先解释来源，不带着它们继续准备或安装 hooks。
   正常提交进入 hook 后由 Git 设置的环境不属于此处异常；测试临时仓库仍必须清洗继承的 `GIT_*`。
6. 检查 `git ls-files -v` 的小写标记（assume-unchanged）和 `S`/`s`（skip-worktree），
   以及稀疏检出、子模块、过滤器和权限比较配置。它们可能改变内容可见性或检出语义。
   有标记不等于文件已修改，但普通 diff 不足以作为完整证明；先解释并在获准的完整隔离树核验，
   不自动清除用户标记或更改 Git 配置来制造“干净”。特殊仓库布局不走未审查的普通路径。

本轮完整日志与必要的范围快照优先放在仓库外独立目录，公开前脱敏。不新建一套缺陷账本；
已发布缺陷继续按 `AGENTS.md` 使用 `quality_trend.py` 的真实时间规则。

### 身份异常的最短出口

先用 `git var GIT_AUTHOR_IDENT`、`git var GIT_COMMITTER_IDENT` 看实际身份，再用
`git config --show-origin --get-regexp '^user[.](name|email)$'` 查配置来源。
仓库配置可能覆盖正确的全局配置；近期多笔提交都用了同一占位身份，也不能证明用户认可。
同一已确认身份不重复询问；身份或授权变化时重新确认作者和提交者，
不因用户已经授权提交就自动批准非预期身份。

用户仅批准本轮身份时，可在身份读回及本次提交命令上同时指定 `GIT_AUTHOR_NAME`、
`GIT_AUTHOR_EMAIL`、`GIT_COMMITTER_NAME`、`GIT_COMMITTER_EMAIL`，不设置作者或提交日期。
这些是已确认身份的单次覆盖，不是允许携带 C0 所列的 Git 路由覆盖。

若 `git config --show-origin` 显示仓库本地配置是占位身份，每笔提交都要走这一步。
模板如下，尖括号处填已确认的身份，不把真实邮箱写进本文；已确认身份可从最近一笔用户认可的提交读回：
`git log -1 --format='%an <%ae>' <提交>`。

```bash
GIT_AUTHOR_NAME='<姓名>' GIT_AUTHOR_EMAIL='<邮箱>' \
GIT_COMMITTER_NAME='<姓名>' GIT_COMMITTER_EMAIL='<邮箱>' \
git commit -F <消息文件>
```

只有用户明确要求永久修改时才改全局、仓库或工作树配置；配置命令失败不算设置成功，
不为解决单次身份问题改写其他工作树的配置。C4 必须再次读回提交对象中的两个身份。

## 3. C1：审查行为和选择验证

- 阅读本轮完整差异、新文件、直接调用者与已有相关测试，不能只看统计或提交标题。
  对照需求说明行为变化、成功判据、失败反例和非目标，排查无关重构、兼容性与数据恢复风险。
- 按日常流程选择验证档位。数据相关核对“原始输入、解析、业务结果、界面”；
  保存相关核对“提交值、实际文件、新进程读回、用户看到的结果”。
  界面区分离屏、原生和安装版；源码测试不代替真实用户场景。
- 故障修复保留最小复现和行为回归；无法证明修复前失败时写明缺口，不编造负向证据。
  首次失败、复测、错误、跳过和 flaky 分开保留，不以重跑绿掩盖首次异常。
- 检查密钥、凭据、个人路径、诊断包、用户数据、视频、生成物及环境是否误入。
  新增惰性依赖、资源、脚本时核对直接关联配置，不遗漏包内依赖，但不在此执行打包。
- 本轮必须判据失败、全部跳过、零用例或关键风险未解释时，不以“先存一个提交”报告验收通过。
  先修复或交接阻断项；需要保存未完成工作的特殊安排须另获明确同意，且不标记已验收。

### 按影响补齐关联，而不是只看改过的文件

只对实际涉及的行核对并在同一交接中说明，不要求每次创建依赖清单或逐项打勾：

| 本轮改变什么 | 同时确认什么 |
| --- | --- |
| 公共函数、回调、消息字段或配置含义 | 直接调用者、失败/取消路径及行为测试是否仍匹配；文本搜索不能证明动态引用完整 |
| 依赖、资源或惰性导入 | 按 `AGENTS.md` 核对锁定文件与包配置；源码导入成功不代替产物验收 |
| CLI、测试位置或流程入口 | 示例、帮助、日常主题表与关联测试同步；导航有效不等于测试已执行 |
| 保存格式、默认值或恢复行为 | 旧数据读入、缺失/损坏恢复、保存后新进程读回；涉及回退时明确旧实现能否读取新格式 |

存在无法拆开的前置提交时列出实际 SHA 与顺序，不能用某个未提交文件或“另一任务稍后会补”
作为本轮已完整的依据。新数据格式不能保证向旧实现兼容时先明确恢复边界，必要时取得产品决策；
退回源码不等于恢复用户数据，不在普通提交流程中自动覆盖真实数据或执行数据迁移。

## 4. C2：整理并冻结待提交内容

只对已经审查且获准的明确路径执行 `git add -- <路径...>`。同文件混有并行改动时，
先协调归属或采用经确认的隔离方案，不整文件打包，也不把部分暂存当成测试同源证明。

```bash
git diff --cached --name-status
git diff --cached --stat
git diff --cached
git diff --cached --check
git diff --cached --quiet --exit-code
git ls-files --stage -- .venv '.venv/*'
git ls-files -u
git diff --exit-code
git write-tree
```

- `--check` 必须通过，无未解决冲突、意外删除、链接或权限变化；`.venv` 本体和内部文件不得跟踪。
  新文件、重命名和删除逐项审查，不能仅凭忽略规则判断安全。
- 此处 `git diff --cached --quiet --exit-code` 的预期是 **1**（存在待提交差异），不是失败；
  0 表示空提交，其他非零表示命令异常。与后面的工作文件一致性检查预期 0 分开记录。
- 记录 `git write-tree` 的结果为 `REVIEWED_TREE`：它是全部待提交内容的标识，不是 HEAD。
  空提交不走普通路径；不为形成记录使用 `--allow-empty`。
- 当前 `pre-commit` 测的是工作目录，不是独立提取的暂存内容。正式验收前要求跟踪文件与暂存内容
  一致，即 `git diff --exit-code` 返回 0，并逐项核对所有未跟踪文件是否影响执行或构建输入。
  非零不等于可以丢弃并行修改，而是当前工作目录不能直接证明该提交已通过。
- 若并行内容造成不一致，保留原现场，先约定隔离方式；如使用独立验收工作树，必须重新核验其
  环境、hooks、完整树及原工作树映射，不复制其他工作树关卡戳，不把它的结果冒充本树通过。
- 从此到提交完成不再改变验收输入或索引；其他会话同时修改相关内容时暂停，重新审查并验证。

### 集中预检：先拦便宜且致命的问题

完成本轮准确路径整理后执行一次，`--path` 逐个列出所有预期变化的文件；
重命名须同时列出旧路径和新路径，不接受目录、通配符或 `.` 代替范围：

```bash
SF_RERUN_FAILED=0 ./.venv/bin/python3 -m tools.commit_preflight \
  --path sf_quote.py --path tests/test_quote_runtime.py
```

上面仅为命令示例，替换为本轮真实路径；已记录起始 SHA 时追加 `--expected-head <完整SHA>`。
工具不自动暂存、不安装 hook、不清除锁或操作状态、不执行测试、不运行提交、不写关卡戳。
它集中检查：特殊路由/短路环境、异常 Git 操作和锁、精确暂存范围、隐藏索引标记、未暂存跟踪变化、
未跟踪潜在执行输入、冲突/子模块/`.venv` 入库、替换引用、实际 hook 及抽样期间 HEAD/索引/状态变化。
文件名使用 Git 的 NUL 分隔输出解析，支持空格、换行和非 ASCII，不拿逐行切割当路径列表。
仓库内自定义位置的实际 hook 只有与已跟踪源码核对一致且可执行时才识别为已知入口，
不因此忽略同目录的其他未知脚本；预检不执行外部 diff，也不执行配置的检出过滤器。

退出 0 仅表示 `checks_passed=true`，可以继续人工核对和正式检查，不代表已获授权、完整关卡通过、
提交成功或持续没有并行写入。JSON 的 `not_checked` 列出未覆盖的判断，尤其是 ignored 依赖、
运行时版本、业务审查和实际提交读回。非零按 `issues` 处理，不删现场、不盲目重试。
默认查询整轮预算 15 秒、单个 Git 查询最多 5 秒；超时或命令异常一律阻断，不降级为通过。
这不是操作系统强制的全进程截止时间：解释器启动和少量本地文件读取不受 Git 子进程超时覆盖。
输出含本地路径，公开前脱敏；不输出质量/路由环境的具体值。

预检输出还带 `screen`（`locked` 与 `display_asleep`，读不到记 `null`）和 `warnings`。
这两项**只提示、不拦截**：屏幕锁着或主显示器休眠时，依赖真实合成或屏幕状态的用例会成簇误红，
与代码无关，重跑多少次都一样（2026-10-21 实测：锁屏下整档 26 条红，同码屏幕醒着全绿）。
锁屏不等于显示器休眠，`pmset` 日志看不到锁屏，所以直接读会话锁定位与显示器休眠位。
看到 `screen_locked_*` 或 `display_asleep_*` 警告时，先让屏幕解锁再起正式提交，
钩子要跑约 13 分钟，起跑后中途锁屏同样会误红。`screen_state_unreadable` 表示没读到，
不能当成“没锁”。产品里的 `sf_presence.screen_unavailable()` 读不到时按“没锁”处理，
那是省电的安全方向，预检不沿用。

### 并行修改的可执行出口

全仓存在并行修改时先选路径，不把“保持并行修改”误写成“仍可直接在该目录验收”：

- **原工作树路径**：仅在已跟踪文件与待提交内容一致、未跟踪输入不污染验收时使用。
  无关的未跟踪非执行资料可以保留；未跟踪源码、测试或配置不能因“不准备提交”就忽略。
- **隔离路径**：原树不能满足上述条件时，取得隔离方案的同意，在明确起始 SHA 的独立分支/工作树
  只还原本轮获准差异；不要求原树先暂存、不清理原树、不自动 stash。
  可用 `--binary --full-index` 补丁传递已跟踪差异，新文件另外明确列入；不要用通配复制整个目录。
  索引与工作文件混有不同改动时先明确选取来源，不能拿一个未解释的补丁覆盖混合状态。
  核对新树相对起始 SHA 的文件、模式和实际内容与批准范围相同，补齐被忽略但必需的本机运行环境，
  仅环境可共享，源码/测试/证据不可借用。然后在该树从 C0 开始独立检查、正常 hook 提交和 C4 读回。
  原树及其分支不随之移动；交接明确实际提交所在分支/路径，后续合入另走既有合并流程。
- 两条路径都无法保证内容归属或运行依赖完整时，停在待提交/阻断。不能把同名版本、相同补丁标题、
  原树测试结果或不同工作树的关卡戳当成隔离树的验收证据。

对未跟踪及 ignored 文件都按“是否被实际执行、导入、读取”判断影响；复用已有依赖锁定和
运行路径隔离规则，不全盘扫描或清理本机。依赖仅在本机未提交文件中存在时，补齐交付内容后重验，
不能让“本机可运行”掩盖新检出源码缺文件。Git diff 会受上述索引标记及过滤/权限配置影响，
不能替代这一步内容与环境核查。

### 执行途中范围变化

- 用户追加“其他已完成内容一起提交”时，重新列出本轮、其他已完成和仍进行中的内容。
  重新审查新增差异、直接依赖和测试，不把全仓有修改等同于全部已完成；其他会话尚未完成的
  分支不自动纳入。可按用户明确允许的范围组合保存，仍须说明每组用途和未验证边界。
- 同一工作树的 hook 仍在运行时不修改源码、索引或验收输入，也不启动第二笔提交。
  能安全完成的先按原范围闭合；新增范围随后从受影响阶段继续。提交完成后再提出的流程修订
  属于下一笔提交，不能沿用前一笔的完整日志证明修订版已验收。
- 扩围会使原路径清单、预检和 `REVIEWED_TREE` 失效。即使源码字节及构建指纹没变，
  仅把已有未跟踪文件或另一组差异纳入索引，也必须重新审查树并预检，正常 hook 不省略。
- 已完成隔离提交但未合入原树时，原树对应修改仍可能显示未提交。先对照两个 SHA 和内容，
  不重复应用补丁，也不自动合并、重放或移动原分支。若扩围后改在原树直接保存完整版本，
  必须确认原树 HEAD、实际完整差异和新的授权范围，独立完成 C0-C4；隔离检查不替原树验收。
  交接写明最终提交所在分支、两个提交的内容关系及临时树去向，不把重复包含写成已合并。

同一文件混有两个任务时按差异归属拆分，不只按文件名判断。测试兼容调整也有依赖：例如测试
改用新脚本变量名，必须与实际脚本改名配套；只提交界面时不能顺带带入该测试调整。

## 5. C3：核验真实入口并正常提交

### 入口核验

```bash
./.venv/bin/python3 --version
./.venv/bin/python3 -c 'import PyQt6'
git config --show-origin --get core.hooksPath
git rev-parse --path-format=absolute --git-path hooks/pre-commit
./git-hooks/install-hooks.sh
```

要求工程 Python 3.14.7、PyQt6 可导入。未配置 `core.hooksPath` 时查询返回 1 是正常配置结果。
这些入口参考命令按需执行：只读预检已核对当前实际 hook 的路径、内容与可执行性时，
本轮无需再运行安装脚本；只有缺失或需要协调更新时才转安装流程，不为核验重复执行 chmod。
安装工具只核验/安装实际 hook，不执行测试；遇不同内容的已有 hook 必须停止，先审查、获准备份
并协调处理，不能覆盖。共享 hooks 可能影响其他工作树，不能写死 `.git/hooks/pre-commit`。

提交前排除会跳过或缩窄检查的遗留环境：`SF_GUARD_PROBE` 必须未设置或为空（非空字符串 `0`
也会短路）；`SF_SKIP_COVERAGE`、`SF_RANDOM_ORDER`、`SF_PUBLIC_REGRESSION` 不得启用。
核对覆盖率比较基线、测试筛选及其他质量相关环境，不降低覆盖率、改基线或隐藏失败来过关。
不使用 `--no-verify`、临时禁用 hooks、手工写戳或复制戳。
提交检查显式设置 `SF_RERUN_FAILED=0` 保留首次失败；覆盖率文件/配置、用户数据重定向等环境
按现有约束核对，不批量打印可能含密钥的全部环境，也不盲目清空合法的隔离变量。

紧邻提交前再次确认 C0 起始 SHA、分支、`REVIEWED_TREE`、跟踪文件一致性和实际 hook 内容未变化，
不要等 C4 才发现提交期间已换了入口或基线。保存以下只读输出作为本轮构建输入快照：

```bash
./.venv/bin/python3 -c 'import json; from tools.gate_stamp import current_info; print(json.dumps(current_info(), sort_keys=True))'
```

记录其中 `fingerprint` 与输入数；C4 以同一命令再取一次，比较 fingerprint/输入数，而不是比较
整个 JSON（提交后 HEAD 本来就会变化）。这个指纹仅覆盖既有名单，**不是所有提交文件的哈希**；
文档等名单外内容由 `REVIEWED_TREE` 和实际 tree 的核对保护。它也不覆盖所有 ignored 运行依赖，
不能代替 C2 的依赖核查。前后相同仍不能证明期间从未改动，验收窗口须协调停止相关并行写入，
不能仅凭事后快照宣称持续隔离。

### 执行及判定

1. 提交授权、范围、`REVIEWED_TREE` 及跟踪文件一致性确认后，正常执行 `git commit`。
   提交标题沿用仓库已有格式：`feat:`、`fix:`、`refactor:`、`test:`、`docs:` 或 `chore:`，
   简短说明本轮目的；复杂变更正文写原因、行为、验证和遗留边界。标题不写未经验证的完成结论。
   标题描述实际变化，不使用仅有“优化/修复问题”的空泛说明；正文在需要时回答“为何改变、用户行为
   如何变化、证据与限制在哪”。小提交不强制长正文，不粘贴原始日志、密钥或私人诊断资料。
2. 提交命令的标准输出和错误输出保留到新的独立日志，记录该命令原始退出码。
   不用 `command | tee log` 的最后一项退出码冒充提交成功，也不覆盖旧失败日志。
   正常 hook 已执行本树完整关卡且证据有效时，不为形式在提交前后重复跑同一轮。
3. 所有普通提交，包括纯文档提交，仍执行现有 hook 的语法检查和完整 `run_tests.sh`；
   日常轻量验证档位不构成提交检查豁免。完整关卡包括现有静态、桥接、布局、回归及覆盖率要求。
4. 完整日志须证明实际执行全量关卡、退出码 0，并有
   `== 全部测试通过，可进行打包发布 ==`；再执行 `./.venv/bin/python3 tools/gate_stamp.py check`
   确认当前构建输入。仅有结束文字、旧戳、probe 成功或提交 SHA 都不足以证明完整关卡通过。
   脚本的“可进行打包发布”文字不构成打包发布授权。
5. **同一时间只许一轮完整回归**（2026-10-21 起）：`run_tests.sh` 取两把锁，一把按临时目录
   （保护共享的 `sf_*_test` 落盘文件），一把按本棵树的 `build/`（保护覆盖率回执）。
   别的会话已有一轮在跑时，本轮以**退出码 75** 拒绝并打印持有者的进程号、启动时刻和目录，
   与“正式版在运行”的退出码 2 分开。看到 75 就等对方结束，不排队、不强杀、不删锁文件；
   只有确认持有者进程已不存在而锁仍在时才手动处理，持有者已死或进程号被复用时脚本会自行回收。
   等待时盯输出里打印的**那个持有者进程号**（例如每隔几秒查它是否还在），不要用 `pgrep -f` 去整机找“安静”：
   别的会话命令行文本里恰好含 `run_tests.sh` 之类字样也会命中，等待会被无关进程拖长甚至永不结束。
   提交钩子跑的就是 `run_tests.sh`，所以两个会话同时提交，后到的一方会被拦住而不是互相污染。
   不要用私有 `TMPDIR` 绕开：测试结果对临时目录敏感，且同一棵树共用的覆盖率回执仍会撞车。
6. 正式版运行守卫阻止检查时，保留现场并请用户安排退出，不强关用户应用、不绕过守卫。
   请用户退出之前，先用 `pgrep -lf` 看命中的是哪条命令行：守卫按完整命令行匹配，
   别的进程的命令行里若含 `/Applications/Skyrocket.app/Contents/MacOS/Skyrocket` 这串路径也会命中，
   那种情况不是正式版在运行，不要去打扰用户。
   首次失败若发生在交易日 09:15 到 09:29，先看失败用例是否在读真实时钟：已知两处依赖这个时段的用例
   在 175bd5c 里固定了时钟，但这不证明整档在该时段都不依赖当前时刻，别把这类红直接归因于本轮改动。
   提交报错、超时、终端断开或日志不全时先读回 HEAD、父 SHA、tree、索引和工作目录，
   **不能先假定没提交就重试**。HEAD 未变化且无新提交时保留日志和暂存内容，修复后从受影响阶段重做；
   确认已产生本轮提交时进入“已提交，待核验”；无法确认时记“阻断（提交结果未明）”。
   两者都停止续作，不自动重复提交或改写历史；不能把未知写成已经提交。
   后续消息钩子、签名、编辑器或命令包装失败也需要检查，不能把所有非零都归因于测试。

提交日志的最小执行写法如下。仅在 C0-C3 前置条件和授权满足后使用；`COMMIT_TITLE` 先设为本轮
实际标题，示例不自动生成标题，不执行合并、推送或发布。整段由 Bash 执行，不逐行搬用到未知 shell：

```bash
: "${COMMIT_TITLE:?请先设置本轮已审查的提交标题}"
EVIDENCE_DIR="$(mktemp -d "${TMPDIR:-/tmp}/skyrocket-commit.XXXXXX")" || exit 1
if QT_QPA_PLATFORM=offscreen SF_RERUN_FAILED=0 git commit -m "$COMMIT_TITLE" >"$EVIDENCE_DIR/commit.log" 2>&1; then
  COMMIT_RC=0
else
  COMMIT_RC=$?
fi
printf '%s\n' "$COMMIT_RC" >"$EVIDENCE_DIR/commit.exit-code"
exit "$COMMIT_RC"
```

`exit "$COMMIT_RC"` 不能省：少了它，整段脚本的退出码是最后那个 `printf` 的 0，后台任务通知就会
报"exit code 0"而真正的提交是 1（2026-10-23 实测两次）。通知里的数字只当线索，**以
`commit.exit-code` 文件为准**。证据目录创建失败则停止，不落到相对路径写日志；执行后无论退出码
如何都读回现场。
临时目录可能被系统清理，需长期复核时按已有证据归档方式保存脱敏日志，不把 `/tmp` 当永久凭据。

长检查期间只读查看原始日志，按语法、前置关卡、全量测试和覆盖率阶段报告进度，
不频繁重复无变化的状态，不把预计耗时当实测。负向用例会主动输出错误、拒绝或并发修改提示；
单个 `ERROR` 或 `!!` 字串既不能证明整轮失败，也不能被一律忽略。以具体用例结果、最终汇总、
完整关卡结尾和原始退出码共同判定，失败保留原日志，不通过重跑覆盖。

本文仅增加只读预检，不新增提交执行脚本或修改 hook 的既有行为；范围、树一致性、授权和证据审查仍由执行者负责，
不能宣称 Git 会自动强制本文全部步骤。

### 排队与等待期间能做什么（2026-10-23 补）

完整关卡约十几分钟，别的会话占着回归锁时还要再排。这段时间不必干等，但有一条硬边界：
**被验的那棵树和暂存区在关卡结束前不许动**（不改源码、不新增测试文件、不 `git add`），
否则验的就不是要提交的内容。边界之内可以提前做：

- 在另一棵独立工作树里推进下一件事的调研、只读审查和起草；
- 把交接文字、提交说明和 C4 的读回命令写好，放在仓库外的证据目录；
- 排队前先做不占锁的事：便宜检查和改动覆盖率预判（下面两个工具）；
- 发版时提前读基线、备份旧包、在仓库外起草质量记录。

仍然不可以：改被验树里的任何文件；用私有 `TMPDIR` 绕开锁；用 `pgrep -f` 去整机找“安静”；
强杀或删别人的锁；跳过 hook。

两个工具把这些固化下来，都不替代完整关卡，也不扩大提交授权：

- `tools/change_predict.py`：只跑与改动相关的用例，用与正式关卡同一把尺子预判“改动行覆盖率”会不会红。
  结论只是预警：子集没漏行不等于整档一定过，子集漏行也不等于整档一定红；选不出相关用例、选得太多、
  数据读不出时如实报“无法预判”（退出码 3），不报绿。`--path` 可把范围限定在自己要提交的文件，
  主树里有别人的脏文件时必须用它。正式版正在运行时它拒绝运行，因为子集用例会与正式版共用用户数据目录。
  保护目的与 `run_tests.sh` 的守卫相同，但口径更窄：预判只按进程名精确匹配（`pgrep -x`），
  不像整档守卫那样还扫命令行里的安装路径，免得被别的会话命令行里恰好含这串路径的进程误拦。
- `tools/gate_queue.py`：`status` 看两把回归锁现在是谁持有；`wait` 有界地等锁空出；
  `commit` 先冻结 HEAD 与待提交文件的哈希，**再问一遍现场能不能提交**（暂存区非空、没有待提交改动、
  HEAD 与预期不符等，当场退出码 2，不领票、不排队，免得排完队才发现），然后做便宜检查和预判，
  红了就不排队（退出码 5），通过后领票排队；`--wait-timeout` 是整次排队的**累计**等待预算，
  输掉抢锁后重新排队也不会重置，轮到自己再核对一次冻结的输入（变了退出码 4），才调
  `release_wrapup commit` 走真实 hook。只有 hook 打印“已有另一轮完整回归”时才当作输掉抢锁并重新排队，
  别的失败立刻停，绝不用重试掩盖真红。`--timeline` 写出事件时间线，把“等别人”和“关卡本身”的耗时分开；
  不加 `--apply` 只做预演。
- `gate_queue.py merge-commit`：给已经 `git merge --no-ff --no-commit` 出来、尚未提交的合并排队提交。
  必须同时给出审查过的 `--expected-head`（合并前 HEAD）、`--source`（被合入的提交）、`--expected-tree`
  （`git write-tree` 的索引树）；排队前后任何一样变了，或工作文件与索引不一致，都拒绝提交
  （排队前退出码 4，轮到自己时同样退出码 4）。合并不是“暂存几个文件”，所以不走 `commit` 那条路径，
  也不做改动覆盖率预判，只做便宜检查；其余的等待预算、重试条件、时间线与 `commit` 共用同一份实现。
  提交后核对两个父提交恰为 `[expected-head, source]`、提交树等于审查树、`MERGE_HEAD` 已清、身份正确。
  把主线快进到这个合并提交不归它管，仍按 `docs/BRANCH_MERGE_WORKFLOW.md` 的 M3-M5 另行核对。

用时也有了账：`run_tests.sh` 每轮把按模块的用例耗时写到 `build/test-durations.json`
（`SF_TEST_DURATIONS_OUT` 可改路径，设为空串关闭）。这是观测，不参与任何判定；
覆盖率采集下的数字偏大，不能与未采集的数字直接比。

## 6. C4：提交后独立核对

提交命令结束后无论成败都要读回结果，不能只相信退出码或最后一行提示：

```bash
git rev-parse HEAD
git rev-list --parents -n 1 HEAD
git rev-parse 'HEAD^{tree}'
git show --format=fuller --stat HEAD
git diff HEAD --exit-code
git diff --cached --exit-code HEAD
git write-tree
git status --short --branch
./.venv/bin/python3 tools/gate_stamp.py check
```

- 实际提交的唯一父提交应为 C0 起始 SHA，树应等于 `REVIEWED_TREE`，身份、标题和文件范围
  与授权相符。HEAD 意外移动、hook 改索引或父提交数量异常时停止，不把别人的提交算成本轮成果。
- 重新读取当前索引树，要求也等于实际提交树，且 `git diff --cached --exit-code HEAD` 为 0；
  `git diff HEAD` 只比较工作文件和 HEAD，不能单独排除提交后索引又被钩子或其他会话修改。
- C3 与 C4 的构建指纹、输入数一致，完整日志和本轮有效关卡戳对应；记录 gate stamp 的路径及指纹，
  不以戳内记录的旧 HEAD 不同于新提交为由重跑，也不以旧戳恰好匹配代替本轮完整日志。
- 工作文件与实际提交一致，未跟踪输入已核对；对照 C0 范围确认并行内容仍保留。
  要求的是本轮内容无遗漏、无夹带，不是为得到“全仓干净”清掉其他人的工作。
- 提交后输入变化、tree 不符、日志缺失或完整关卡不可证明时，标记“已提交，待核验”，
  不标记验收完成。先找原因；不自动 amend、reset、rebase、revert 或强推改写现场。
  修复原则上用新的普通提交，仍须明确授权并重走本流程。
- 提交后其他会话继续写入时，区分“固定 SHA 的验收证据”与“当前工作树的新差异”：
  不能给变化后的工作树沿用通过结论；若本轮提交证据尚未闭合，仍保持待核验，不为清差异回退他人工作。

## 7. C5：交接与结束判据

使用 [DAILY_WORK_TEMPLATES.md](DAILY_WORK_TEMPLATES.md) 的“提交交接”，小提交在对话中记录即可；
不强制新增逐次报告或改写发行交付单。必须分开表述以下结果：

| 状态 | 可声明的事实 | 结束条件/下一步 |
| --- | --- | --- |
| 待提交 | 修改、审查或验证已进行，尚未形成提交 | 缺授权则等待；缺判据则补齐 |
| 阻断 | 检查失败、现场冲突、证据不足或提交结果未明 | 记录具体失败和最小恢复动作，不推定提交已产生或验收通过 |
| 已提交，待核验 | 本地已有提交，C4 尚未全部满足 | 停止后续操作，核对实际树和有效证据 |
| 本地提交已核验 | 授权范围、实际提交、完整关卡及同源核对全部满足 | 交接 SHA、行为、证据、未验证项；本流程结束 |

“本地提交已核验”不等于产品已安装、真实场景通过、远端同步、合并或发行完成。
未完成的真实场景继续保持未验证，不通过措辞消除缺口。

### 隔离工作树的去留（2026-10-21 补）

本轮若新建了 `.sf-*` 之类的隔离工作树，交接时逐棵写明去留，不留成无人认领的旁路目录
（2026-10-21 一天就建了五棵，收尾时没人说得清哪几棵还在用）。判据按顺序核对：

1. 分支最新提交已在主线历史里：`git merge-base --is-ancestor <分支> <主线>` 返回 0；
2. 树里没有未提交改动，也没有尚未归档的证据文件（发布树的 `quality-*.json`、`build/` 里的候选与读回）；
3. 没有进程的工作目录在该树里（`lsof +D <树>` 为空），也不是别的会话刚建、正在用的树。

三条都满足才收拾：先移除里面指向主树的 `.venv` 符号链接（只删链接，不碰主树环境），
再把整棵树**移到废纸篓**而不是 `rm`，最后 `git worktree prune`。分支保留，提交都在历史里，
需要时可重建。发布树（`release/v*`）要等发版证据按发版流程归档后再收拾；任何一条对不上，
就记为“保留”并写明缺哪一条，不凭印象清理，也不收拾别的会话建的树。
适用 `BRANCH_MERGE_WORKFLOW.md` 第 1.1 节的任务分支，合并落地后的树与分支清理按该文 M5 的任务自清理条件办理
（分支只用 `git branch -d`，被拒绝的保留并列出）；那一条已把“获清理同意”视为满足，不要在此重复追问。

上面三条核对和后续动作，发布树可直接用 `tools/release_wrapup.py retire`（默认只预演，`--apply` 才执行）；
发布证据的归档用同一脚本的 `archive`。用法与护栏见
[RELEASE_PREPARATION_WORKFLOW.md](RELEASE_PREPARATION_WORKFLOW.md) 的 P6 第 6 步与第六节。
归档产生的改动按本流程 C0-C5 提交；这一步也可以用同一脚本的 `commit` 完成（见下）。提交通过后，
`push`（默认预演，`--apply` 才推）只快进推送当前检出的开发主线、绝不强推，并按实际 push URL 读回。

### 用脚本完成 C2-C4（2026-10-21）

```bash
./.venv/bin/python tools/release_wrapup.py commit --path <文件> [--path <文件> ...] -m <消息文件>          # 预演
./.venv/bin/python tools/release_wrapup.py commit --path <文件> ... -m <消息文件> --apply --log <日志>  # 提交
```

`--apply` 做的事和手工一致：确认 HEAD 是分支且（给了 `--expected-head` 时）未变、索引里没有别人暂存的内容、
每个路径确实有待提交改动；只 `git add` 点名文件；跑 `commit_preflight`，不过就撤销暂存并列出原因；
通过后 `git commit -F` 走真实 hook，**没有任何跳过 hook 的选项**；提交后核对：新提交直接接在计划时的 HEAD 上、
提交树等于预检时写出的树（hook 改了索引会当场报错）、改动文件恰好是点名的那些、作者与提交者等于计划的身份。
身份默认取 HEAD 的作者，`--author "名字 <邮箱>"` 只对这一次提交生效，不改仓库配置。

完整 hook 要十几分钟：用后台方式运行并写 `--log`，以脚本退出码为准，不要用“看到输出”判断完成。
`--timeout`（默认 1800 秒）到点会停掉整个进程组，包括 hook 自己拉起的子进程，并提示先看 `git log` 与 `git status`。
hook 失败或预检不过时，脚本只撤销它自己暂存的路径，工作区里的修改原样保留。
脚本不判断范围与授权，也不替你写提交消息；`--apply` 前仍须完成 C0 的授权、范围和现场确认。

### 中断接续与证据保管

换聊天或中断后先按 [日常交接规则](DAILY_WORKFLOW.md) 第 9 节核对现场，
再确认最后命令是否仍在运行、是否已产生提交、停在哪个 C 阶段；不自动启动第二个提交或清理残留进程。
记录一个明确的下一步及其前置条件，区分需用户决定的行为变更与执行者可继续完成的只读检查。
没有同源证据的旧结果仅作线索；有有效绑定的结果不因更换执行者就全部重跑。

需后续复核的证据不只留 `/tmp` 路径：归档到已确认的仓库外私有位置，并记录相对文件名、
实际命令/退出码、来源树/输入指纹及必要文件摘要；路径不存在或摘要不符时不继续引用为有效证明。
原始失败与复测分开，公开摘要与私有原始记录分开，不为归档自动上传、提交原始日志或复制用户数据。

## 9. 可重复验证与工作量控制

```bash
QT_QPA_PLATFORM=offscreen SF_RERUN_FAILED=0 ./.venv/bin/python3 tools/test_runner.py --module tests.test_commit_preflight --module tests.test_commit_workflow --module tests.test_branch_merge_workflow
```

用例只在临时仓库操作，清洗所有继承的 `GIT_*`，不提交本仓库、不访问远端、不操作安装版。
覆盖普通提交、特殊索引标记、钩子前后修改、失败读回、缺失未跟踪依赖、输入指纹与并行隔离等机制。
夹具 hook 仅用于检验 Git 机制，不冒充产品完整关卡通过，也不自动强制执行者遵循全文。

六阶段不等于六份报告：小提交在一个交接记录里引用已有证据，原始日志另存；只有失败、
范围变化或必要判据失效才返回对应阶段。有效的正常 hook 已做完整关卡时，不再额外跑第二轮；
非测试原因导致提交失败后的完整关卡仍按现有 hook 执行，不通过禁用 hook 来省时间。
轻量文档修改不要求无关业务定向测试，但真正提交仍经过现有完整 hook，不新增豁免。

### 时长优化与失效规则

- 预检先做环境和现场阻断，再做范围与一致性检查；失败不进入完整回归。测试/依赖已失败也先修复，
  不为了凑“全量失败证据”继续耗时。不要把“先手动完整回归、再 commit 由 hook 再跑一次”设为默认。
- 正式检查串行执行，不能在同一工作树同时跑完整关卡、并行提交或修改源码来换取墙钟时间；
  只有不会共享源码、用户数据和产物的独立检查可并行。时长优化不减少覆盖率、保护措施或正式必需项。
- 记录实际预检耗时（工具 `elapsed_ms` 是内部计时，不含解释器启动）、定向验证、完整 hook、读回耗时；计时使用单调时钟，
  等待用户退出应用或确认范围的时间单列，不把等待算成测试性能。未知写未知，不填估计值。
- 预检是当下快照，不是可跨轮复用的凭据；相关环境、HEAD、索引、hook 或工作文件变化后失效。
  指纹、树或日志任一条件不满足就重做受影响检查，绝不用旧戳或 `--no-verify` 缩时。
- 定向验证按行为风险选择，不盲目扩大；同一问题多轮修复先重跑受影响用例，稳定后才正常提交。
  新增代码、测试或脚本后不复用旧完整关卡。文档提速与本机预检样本均不证明整套提交周期已缩短；
  需要未来多次同口径实绩，才能比较全流程时间、失败返工率与稳定性。

## 10. 流程维护

- 不只看耗时，也观察范围遗漏、误报阻断、首次失败、重复执行和交接后重新调查等情况。
  复用既有任务记录和缺陷账本，不新增强制遥测或第二套台账；没有足够样本不宣称质量改善。

  工具仅承担可重复的机械检查，不能逐渐替代授权、业务判断或永久质量政策。
- 新增强制步骤前，说明要拦什么、正反例、常见误报、额外成本和失败后的出口；变更后同步工具、
  导航、模板与验证。纯操作建议不要暗中升级为门禁，既有正式要求也不能借流程精简降级。
- 日常仍按四个操作执行；上述关联、恢复和记录要求只在实际涉及的阶段处理，不新增审批轮次、
  固定报告数量、跨会话自动消息或未经授权的真实外部操作。
