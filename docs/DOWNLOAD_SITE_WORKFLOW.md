# Skyrocket 下载站改版到上线标准流程

制定日期：2026-10-30。适用：下载页 `services/download-analytics`（Cloudflare Pages 项目 `skyrocket-downloads`）
的改版、预览、上线和回滚。这是操作规约，不是自动执行器，也不代表已经执行过任何一步。
提交、合并、发版仍分别走 [COMMIT_WORKFLOW.md](COMMIT_WORKFLOW.md)、
[BRANCH_MERGE_WORKFLOW.md](BRANCH_MERGE_WORKFLOW.md)、[RELEASE_PREPARATION_WORKFLOW.md](RELEASE_PREPARATION_WORKFLOW.md)，
本文不重定义它们的步骤和授权，只规定下载页这条线怎么接上它们。

## 1. 一句话流程

先出效果图，你选一版；然后改源码并提交；再用预览命令得到一个预览网址，你在浏览器里看；
你说“敲定”，才合入主线并上线；上线后自动核对；出问题时，由你明确要求才回滚。

| 阶段 | 做什么 | 谁拍板 |
| --- | --- | --- |
| 0 效果图 | 只出效果图，不改源码；每版一份新文件，不覆盖旧版 | 你选哪一版 |
| 1 落地 | 在独立分支里改源码、测试全绿、提交 | 不另需拍板（任务范围内的本地提交，沿用持续执行授权） |
| 2 预览 | `npm run preview`，得到预览网址 | 你在浏览器里看 |
| 3 敲定 | 你回答“敲定 / 可以上线”或“再改” | 你 |
| 4 上线 | `npm run ship -- --dry-run`，再 `npm run ship` | 阶段 3 的“敲定”即授权 |
| 5 读回 | 部署自带读回，再跑 `npm run status` | 不需要；读回不过就停 |
| 6 回滚 | `npm run rollback -- <部署编号>` | 你明确要求才做 |

所有 npm 命令都在 `services/download-analytics` 目录下执行。预览没经你确认前，绝不合并、绝不上线。

## 2. 为什么要有这套流程

原先的做法有六个问题，都是实地查到的：

1. 线上这一版查不到出处。Cloudflare 上最近 8 次正式部署的提交号全为空，且全部标记为带未提交改动，
   事后无法回答“线上这一版对应哪次提交”。
2. 预览命令挡错了东西。旧的预览命令检查整个仓库是否干净，主树里有 11 行与站点无关的未提交文件就拒绝运行。
3. 上线没有门槛，也没有回滚点。旧的部署脚本直接读工作区构建，不要求内容已合入主线，
   也不记录上一次部署编号，回滚要靠人去翻。
4. 可能公布线上还没有的安装包。若主线的 `APP_VERSION` 先于 OTA 发布被提高，此时部署会在页面上公布
   线上还没有的安装包（DMG 下载 404）。
5. 主树默认没有 wrangler（Cloudflare 的命令行工具）。`services/feedback-worker/node_modules` 被 git 忽略，
   部署会直接找不到它。
6. 线上跑着主线里没有的内容。2026-10-30 第一次运行 `npm run status` 就报了 `drift`：正式站部署的是任务分支
   `task/scene2-motion-20261030` 的提交 639651c（第二张卖点图改为动图；线上 `scene-2-alert.mp4` 的素材指纹与该分支里的
   文件一致，当时主线里没有这个文件）。用户已同意上线，它是先部署、后合并；合并时又被主树里另一份未提交的
   `deploy-pages.mjs`（正是编写本流程时的改动）挡住，后来以 a157e70 合入主线。合入之前，下次发版第 6.1 步从主线
   部署会把它悄悄撤回。

## 3. 每个阶段

### 阶段 0：效果图

你会看到：几张效果图，每改一轮就多一份新的，旧的原样保留，方便来回比。你选定其中一版，才进入阶段 1。

- 只出效果图，不改 `services/download-analytics` 下任何源码。
- 沿用 `outputs/site-redesign-<日期>/<名字>-vN/` 的做法：每版一个新目录，不覆盖旧版。
- `outputs/` 不进公开源码快照，渲染脚本和中间文件放这里。

### 阶段 1：落地

你会看到：一段说明“已在某个分支里改好，测试全绿，已提交”。这一步不会碰线上。

- 在独立分支或独立工作树 `task/<名字>` 里改 `services/download-analytics`，不在主树里直接改。
- 改完先跑 `node --test tests/*.test.mjs`，必须全绿。
- 按 [COMMIT_WORKFLOW.md](COMMIT_WORKFLOW.md) 的 C0-C5 提交。提交钩子经
  `tests/test_download_entry_node_suite.py` 会把这组测试再跑一遍，所以钩子红了就是站点测试红了，修好再提交，不绕过钩子。

### 阶段 2：预览

你会看到：命令跑完，最后输出一行 JSON，里面有 `preview_url`。你打开这个网址，就是即将上线的页面。
在这个预览页上点下载，不会计入正式统计。

```bash
cd services/download-analytics && npm run preview
```

- 预览只要求页面内容已提交（工具脚本未提交不影响预览出的页面；上线才要求全部站点输入干净）。
  只看 `services/download-analytics` 下除 `README.md`、`ASSETS.md`、`tests/`、
  `asset-sources/` 之外的文件（`dist/`、`node_modules/`、`.wrangler/` 也不算），再加图标导出会一路引用到的五份
  Python：`sf_constants.py`、`sf_icons.py`、`sf_instance.py`、`sf_logging.py`、`sf_privacy.py`（测试会从
  `export-icon.py` 出发按 import 推算，名单漏一份就红）。主树里别的未提交文件不挡。
  有未提交的、或被 git 忽略却会被打进部署包的站点文件（例如误落进 `public/` 的 `.DS_Store`）时，命令直接拒绝并列出文件名。
- 用线上当前版本号构建，部署到独立的预览分支 `review-<提交前 12 位>`，绑定独立的预览数据库。
- 提交说明里带两个 16 位指纹：`page:<页面指纹>` 与 `tool:<工具指纹>`。页面指纹只由"决定页面长什么样"的文件
  算出（页面模板、素材、构建脚本、图标相关 Python），改工具脚本不会让它变；工具指纹记的是部署脚本这一组。
  两者都不看分支名、提交号，也不看合并方式。只有页面指纹变了才需要重新预览。
- 部署后核对：预览页和 `/health` 正常，页面里的每个视频都支持分段请求，并且没有改动正式环境（正式部署编号和
  正式配置都不变）。核对不过，命令失败。
- 预览要等你在浏览器里确认。命令成功只说明预览页能打开、没动正式环境，不说明你满意。

### 阶段 3：敲定

你会看到：会话把预览网址交给你，问一句“预览看过了，敲定上线吗”，然后等你回答。

| 你说 | 接下来 |
| --- | --- |
| “敲定”“可以上线” | 视为授权合入主线并上线，进入阶段 4 |
| “再改” | 回到阶段 1；只要改过页面内容，页面指纹就变了，必须重新预览（只改工具脚本不变） |
| 没说清 | 什么都不做，不合并、不上线 |

- 合并按 [BRANCH_MERGE_WORKFLOW.md](BRANCH_MERGE_WORKFLOW.md) 的 M0-M5 和第 1.1 节执行（分支须是执行者自建、
  已提交、审查闭环；起跑前核对别的会话、交易日 09:15-09:29、正式版是否在运行、屏幕是否锁定）。
  合并本身不含推送；上线由阶段 4 的 `ship` 单独完成。
- 合并不改变页面指纹，所以合并前预览过的页面，合并后仍对得上。主线上如果同时有别人合入的页面改动，
  指纹会变，上线前的检查会因此找不到对应预览，需要重新预览。
- `sf_constants.py` 也在页面指纹里，所以每次发版升版本号，之前做的预览都作废，要重新预览。预览按“预览那一刻的线上版本号”
  构建，`ship` 上线前会重新读回这个预览，版本号和现在的线上版本对不上就不算数。

### 阶段 4：上线

你会看到：先是一份检查结果（`ready` 为真或假，外加 `problems` 清单）。有问题就以退出码 1 结束，什么都没有部署；
全部通过时同样先打印这份结果（`ready` 为真、`deploying` 为真），再开始部署。
部署成功后最后输出一段 JSON，里面的 `previous_deployment_id` 是上线前的正式部署编号（回滚点），
`rollback` 是现成的回滚命令。这段 JSON 要留住，阶段 6 要用。

在主线检出（分支 `feat/target-price`）上执行：

```bash
cd services/download-analytics
npm run ship -- --dry-run --preview <预览部署编号>   # 只检查，不部署
npm run ship -- --preview <预览部署编号>             # 检查通过后部署
```

`--preview` 必须点名一份预览：工具只能证明"存在同页面指纹的预览"，你有没有真的看过，只能靠这个编号来证明。
编号在阶段 2 的输出里（`deployment_id`），dry-run 也会把候选编号打出来。

- 硬条件五条见第 4 节，缺一不上线。
- 通过后先拿锁，再在锁内重读正式部署编号（回滚点）与线上版本号；等锁期间线上版本变了就拒绝，让你重跑，
  避免用一个过期的版本号上线。然后调用 `deploy-pages.mjs`，带 `SF_DEPLOY_COMMIT_HASH` 与 `SF_DEPLOY_COMMIT_MESSAGE`
  两个环境变量，把真实提交号和两份指纹写进部署记录。`SF_PAGES_OUT`、`SF_APP_VERSION`、`SF_DMG_PATH` 这三个会改变
  构建产出的环境变量不会传给子进程。`deploy-pages.mjs` 在构建前和上传前各核对一次：HEAD、站点输入、页面与工具指纹
  还是检查时的那一份，变了就拒绝上线（部署读的是工作区，指纹取自提交，中间被别的会话改动时靠这一步拦住）。
  两个变量必须成对：提交号是 40 位，说明里带 `page:<页面指纹>` 与 `tool:<工具指纹>`，不合规时 `deploy-pages.mjs`
  在动 Cloudflare 之前就失败。
- 部署后确认正式部署编号确实变了、新部署记录带同一个页面指纹，才输出 JSON。
- 部署前会拿一把锁（本机共享目录 `~/Library/Caches/SkyrocketDeploy/deploy.lock`），`ship`、回滚、对账和发版链第 6.1 步共用；
  后到者会看到持有者进程号，不会两边同时上线。同一台机器上的多个克隆也共用这把锁；跨机器的并发仍靠部署脚本上传前再读一次
  正式部署编号（准备期间被别人换过就整次失败，不会把别人的部署记成自己的）。
- 部署前先往 `outputs/site-deploys/journal.jsonl` 写一条"进行中"，成功或失败再补一条；日志只保留最近 500 条。
  进程被杀、输出丢了，`status` 也能看出"上次部署没走完"。只有"进行中且线上已经换了部署"才拦住下一次上线（这时需要人工确认）；
  还停在旧部署的，线上原封不动，不拦；读不到线上编号时只报"未核验"，不当作故障。
- 部署中途失败时，错误信息会写出上线前的编号。先跑 `npm run status` 看线上现状，线上页面不对再回滚。
- 如果上传其实已经成功、只是最后读回超时，`ship` 会再查一次正式站：换成了**同一提交、同一页面指纹**的部署就把日志记成完成
  （附上读回失败的原因），并照常打印回滚命令；退出码仍是 1，因为读回确实没通过。这样慢线路不会把一次成功上线记成失败、卡住下一次。
- 如果进程被打断、日志停在"进行中"，会在下一次 `ship` 前被拦住。人工确认线上之后，用 `npm run reconcile -- --confirm`
  把账收掉：线上已切到**同一页面指纹**的新部署就补一条"完成"，还停在旧部署就补一条"失败"；线上是别的内容时会拒绝，
  不会把别的部署记成你那次——确认过它确实不是这次上线、要放行下一次，再追加 `--abandon` 记为失败。这个入口不会自动执行。

### 阶段 5：读回

你会看到：部署过程中逐项读回，通过才继续；上线后你再看一句结论。

- `deploy-pages.mjs` 内置读回：素材指纹对拍、安全策略头、视频分段请求、四个下载入口 HEAD 请求 302 到 GitHub。
  任何一项不通过，命令失败。读回只用 HEAD，不下载安装包。整轮读回有 12 分钟总时限，超过就失败并释放部署锁，
  不会因为网络一直超时而长时间占着上线入口。
- 素材读回会记一份本机缓存（`~/Library/Caches/SkyrocketDeploy/readback-cache.json`）。下次部署同一份素材时，
  直接用 `If-None-Match` 换 304（304 只带缓存头，类型与体积取自上次完整验证过的缓存），不再重复下载 14MB 正文，
  也不再额外发 HEAD。内容一改，地址里的指纹就变，缓存自动失效、照常整份下载并重算哈希；视频仍逐字节核对首尾两段。
  缺类型/缓存头的旧缓存条目会整份重下一次以补齐。第一次部署新内容仍是最慢的一次。
- 上线后再跑 `npm run status`。它只读，不部署，不需要令牌也能跑出大部分结论（读不到部署记录时，只是无法判断页面指纹戳，
  结论里会写明）。它把线上首页引用的素材指纹与本地构建对拍，并读正式部署记录里的页面与工具指纹。结论有四种：

| 结论 | 含义 |
| --- | --- |
| `in-sync` | 完全一致：线上就是这份站点内容，每个素材指纹都对得上 |
| `assets-match-unstamped` | 素材一致，但线上部署没有页面指纹戳（或是拆分前的旧 `site:` 戳），文字类改动无法排除 |
| `dirty-checkout` | 这份检出里有未提交的站点文件：本地构建读的是工作区，不是已提交的内容，对得上也证明不了线上；先提交或还原再核对 |
| `drift` | 有差异（素材不同、未上线，或线上来自另一份内容），退出码 1；真漂移优先于 `dirty-checkout` |

- `status` 同时会看部署日志：最后一条是"失败"时显示 `last-attempt-failed`（上次没上线成功，不算没走完）；
  最后一条是"进行中"且线上换了部署时显示 `interrupted-after-switch` 并以退出码 1 结束；线上仍停在旧部署显示
  `interrupted-before-switch`；读不到线上编号显示 `journal-unverified`，后两者都不阻塞。

- `drift` 且 `live only` 里有主线没有的素材，说明线上跑的是没合入主线的内容（第 2 节第 6 条）。两种收法都要你决定：
  把那条分支按本流程走完（确认预览、合入主线、`ship`），或者回滚到主线对应的那次部署。不要直接从主线 `ship` 盖过去，
  那等于撤掉别人已经上线的改动。

## 4. ship 的五条硬条件

缺一不上线。每一条挡的都是已经发生或可以预见的事故：

| 条件 | 挡的是什么事故 |
| --- | --- |
| 当前分支必须是 `feat/target-price` | 上线一个只存在于任务分支里的页面，主线里找不到它（第 2 节第 3 条） |
| 站点构建输入没有未提交改动 | 部署记录带“未提交改动”，说不清线上对应哪次提交（第 2 节第 1 条） |
| 站点源码里的 `APP_VERSION` 等于线上 `/health` 报的 `build_version` | 页面公布线上还没有的安装包，下载得到 404（第 2 节第 4 条）；两个版本不一致说明发版在进行中或未完成 |
| Cloudflare 上存在“同一页面指纹、部署成功”的预览，`ship` 重新读回它仍然可用，且 `--preview` 点名的就是它 | 没有经过你看的内容直接上线；也挡住“按旧线上版本号做的预览”“上传后核对没过的预览”和“随手拿一份别的预览过闸” |
| `services/download-analytics` 的 node 测试全绿 | 上线没过测试的代码。`ship` 自己再跑一遍，不信任“刚才跑过” |

## 5. 回滚

你会看到：一行 JSON，写明回到了哪个部署，并读回了健康接口。回滚是独立的、明确的动作，只在你要求时做，
不会因为一次探测失败自动触发。

```bash
cd services/download-analytics
npm run rollback -- <ship 输出里的 previous_deployment_id>
```

- 只接受部署成功的正式部署，且不能是当前这一个；当前部署、预览部署、失败的和查不到的编号一律拒绝。
  编号还必须在 Pages 最近 25 条部署记录里，不在这 25 条里的编号同样被拒绝。
- 回滚后读回 `/health`，数据库没绑上就报错。
- 回滚只改线上，不改主线。出问题的那次提交仍在主线里，发版链第 6.1 步下次会把它再部署上去。
  回滚之后要另做决定：修好再走一遍本流程，还是把那次改动从主线撤掉（撤销走合并流程，另需你同意）。

## 6. 与发版链的关系

- `build_release.sh` 第 6.1 步（以及 `tools/release_resume.py`）仍直接调用部署脚本，但带 `SF_DEPLOY_PROVENANCE=auto`：
  部署脚本自己取发布树的提交号与两份指纹写进部署记录。发版部署因此也可追溯，只是**不要求先预览**（发版本身有关卡）。
- 发版树取自主线，凡是已合入主线的站点改动，都会随下一次发版上线。因此规则是：
  **没打算上线的站点改动，不要合入主线**。预览、敲定、合并、上线要连着做完，不要把合并留在中途。
- 第 6.1 步排在 OTA 发布之后，页面版本和线上清单一致；`ship` 的版本条件（第 4 节）管的是平时单独上线下载页的场合。
- 发版部署会带页面指纹，所以发版后 `status` 通常直接是 `in-sync`；若仍是 `assets-match-unstamped`，说明那次部署来自更早的旧工具，下一次 `ship` 会补上。
- 清理定时任务的源码摘要没变时跳过上传（约省 45 秒）；摘要缓存放在本机共享目录，发版树与主树共用一份。
- `ship` 只部署下载页（Cloudflare Pages 的 `skyrocket-downloads`），不发 OTA、不推送 GitHub、不同步公开源码。
  这些仍按各自的流程和授权判断。

## 7. 前置条件

- node。
- `npm ci --prefix services/feedback-worker`：提供固定版本的 wrangler。`node_modules` 被 git 忽略，装完不会让工作区变脏。
  脚本按自己所在目录找 wrangler，所以每个工作树各装一次。
- wrangler 已登录 Cloudflare：`wrangler auth token --json` 能返回令牌。检查时只看命令成不成功，
  不要把输出贴进对话、日志或文档。
- 钥匙串里有服务名 `SkyrocketDownloadCheck` 的令牌：每次正式部署都要用（`deploy-pages.mjs` 把它装成线上的服务端密钥，
  读不到就在动线上之前失败），预览首次建库时也要用。检查它在不在，不要加 `-w` 把值打印出来。
- 构建会用工程的 `.venv/bin/python` 出图标（环境变量 `SF_PYTHON` 可改）。换一套 Python/Qt 可能让图标像素变，
  `status` 会把它报成 `drift`——这是会暴露的差异，不是假通过；没有特殊原因不要改它。
- 多个会话同时改站点时，各用独立工作树；主树里不留任何未提交的站点文件，包括自己的。`tools/land_branch.py`
  按文件判断重叠，主树里一份未提交的 `deploy-pages.mjs` 就足以挡住别人的合并（第 2 节第 6 条就是这样卡住的）。
