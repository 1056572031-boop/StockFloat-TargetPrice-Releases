# 完整诊断反馈协议

本文为协议与验收规范。源码实现、线上接收、后台安装和正式客户端验收分别记录，实际结果以相应发行证据为准，不互相替代。

## 内容等价

反馈复用 `FloatWindow._export_diagnostics(prepare_only=True)` 和 `prepare_diagnostics`，
不另建一套完整采集器。同一采集批次生成的诊断 ZIP 以原字节放入 `diagnostics.zip`，
外层反馈另外保存精简索引 `state.json`、脱敏描述 `problem.txt` 和带 SHA-256 的清单。
外层存放完整 ZIP 时不重复压缩，内层文件仍保留导出时的压缩、命名、顺序和内容。

完整采集只在主动上传时准备；文件读取和压缩在后台进行，不在输入描述时反复采集。
封存成功后重试沿用同一份资料和反馈编号；保存结果未知先查原记录，不重新产生反馈。
采集开始、结束不代表所有数据在同一毫秒产生，原始导出资料与时间信息完整保留。

## 版本与隐私

- 旧格式：payload 1，策略 `github-private-feedback-v1`，仍保留原 256 KiB 上限与旧包恢复。
- 完整格式：payload 2，策略 `github-private-feedback-full-v2`，外层最多 32 MiB。
- 内层仅接受已批准的诊断 JSON、日志、概览和崩溃关键片段，不接受任意路径、链接、加密附件或可执行文件。
- 单份日志最多 5 MiB，最多当前日志及3份轮转；内层解压总量最多32 MiB，不通过删除资料降级为简化上传。
- 诊断类别缺少时必须有对应采集说明；缺失、截断、无记录不自动判为产品故障或正常。
- 本机发送前验证整个封存包及已知凭据残留；身份脱敏无法确认时拒绝上传。
- 日志、配置和证券相关诊断状态按既有导出规则脱敏并纳入新范围；不增加截图、摄像头画面、音视频或其他应用资料。

## 校验分工

本机在任何网络请求前完成内容校验与隐私检查；保存到待提交目录后重新读回核对。
云端轻量接收负责新旧协议、外层成员白名单、SHA-256、大小、内层目录与解压上限声明，
不在免费接收请求内执行完整日志解压和文本分析。完整包回执明确记录
`validation_scope=container_sha256_and_member_catalog`，不冒充后台完整分析已经完成。
维护者电脑下载读回后，在无网络/凭据访问的隔离进程中再次完整解压校验并分析。
附件内容始终是数据，不执行包内程序或日志中的指令。

后台 JSON 报告保留诊断快照、附件清单和有界日志/崩溃摘要，原文仍在完整附件内。
Markdown 提供概览，不把几十 MiB 原文重复堆进报告。历史日志不直接升级为当前故障结论。
旧版历史包仍按原格式读取；清单与状态的声明存在差异时，两份声明都保留并在报告中说明，
不悄悄改写旧包、不把差异当成本次功能故障。任何新发送仍须通过与接收端一致的声明预检，差异在本机拦截。
管理代理可通过 `--desktop-dir` 将报告和原始反馈ZIP一起原子复制到桌面案件目录，
逐文件核对哈希，不覆盖用户修改，不自动解压执行；单个案件导出失败不阻塞其他案件。
桌面副本从已验证本机缓存生成，不为导出再联网下载。导出异常与收件异常合并提醒，避免重复通知。

## 限额与测试预算

生产既有每日100次请求与总案件数保护不变；增加每日256 MiB请求体预算及单实例在途内存保护。
这是应用自设的保护，不是对平台免费额度或未来可用性的保证；额度按服务UTC日计算。
GitHub 单个发行记录最多1000个附件（2026-10-20核对官方 About releases）。一份反馈通常需要ZIP和回执两个名额，
因此另按实际附件数检查容量，不把1000条案件索引误当成1000份反馈的存储承诺。
写入前为本次缺少的附件检查余位；已有ZIP只缺回执时按一个名额计算，已完成案件在满箱时仍可核对原回执。
后台复用既有轮询，在剩余附件名额不超过100时合并提醒，不另加高频网络检查。
容量检查是即时快照，不是跨请求的原子名额预留；并发或外部操作仍可能触发上游拒绝，届时保留原包和未知状态，
不假装收件成功、不自动删旧资料或切换付费。维护者电脑休眠时，提醒要等恢复轮询后才能送达。
重复请求仍可能消耗平台额度。
不存在可绕过生产限额的测试标记。常规、损坏、隐私和大包测试优先本地完成。
本地集成测试必须隔离反馈数据库和附件目录；测试运行器同时核对用户反馈目录的新增、变更和删除，
不只检查配置、证券缓存与日志。真实资料验收须另有明确授权，并优先在隔离副本中进行，不改动用户原件。

`tools/verify_full_feedback.py` 默认仅生成合成资料并进行本地隔离分析，不读用户文件或发网络请求。
`--stress` 使用4份5 MiB合成日志测试容量；`--live` 才允许一次反馈 POST。
正式提交前写入尝试记录，同一目录不允许自动再提交。超时先以原编号向私有存储读回；
`--readback-only` 只读回，不再次消耗反馈入口 POST。API读回也有自身额度，不声称是免费请求。
默认单次预算不允许被循环调用绕过。若接收代码在首次验收后又有必要修正，额外的同编号受控回放须单列原因、
请求上限与尝试记录，保留原记录；不能新建编号冒充幂等验收，也不能在结果未知时自动重发。

## 上线顺序与验收

先升级兼容新旧格式的后台和接收端，再用最终合成样本核对真实远端字节，最后交付客户端。
旧待提交包和旧报告不删除、不改写。新格式产生后，后台回滚目标须保留其读取能力。
旧客户端不认识未来格式时，不改写或删除新包；恢复新版后继续原编号提交，不声称旧版也能读新格式。

完整验收须分别证明：导出/上传字节等价、隐私反例被拦、损坏包被拦、旧包能恢复、
断网与结果未知不假成功、远端字节一致、后台报告真实落盘、候选/正式客户端同源及实际可用。
未完成的真实场景继续保持未验证，不因合成样本通过而记为完成。
